# 商城功能测试报告

## 测试结论

**上线结论：不可上线（面向真实支付生产环境）。**

模拟支付场景下，会员购买到管理员发货、用户查看物流、管理员完成订单的核心闭环已在真实 MySQL 8 中通过；全量后端回归、管理后台构建和小程序类型检查也均通过。但当前接口没有用于识别“同一购买意图”的稳定幂等键，网络重试可能创建多笔独立待支付单；同时真实微信支付/退款和小程序真机流程尚未联调。商城接口文档仍处于“草案/实现中”状态，且与待审阅方案存在端点差异。

在解决预支付幂等语义、确认商城接口契约并完成真实微信渠道验收前，不应将本提交作为真实资金生产上线版本。若部署目标仅为模拟支付开发测试环境，已实测的主链路可供继续联调。

## 已验证的关键闭环

1. 管理员可在后台创建商品、查看列表、修改资料、上架和下架；会员只能看到上架商品。
2. 会员预支付成功后，即使商品改名、改价或下架，支付仍按原商品和金额快照结算。
3. 模拟支付成功后只创建一笔待发货订单，保存默认收货信息；同一支付单重复支付复用原订单。
4. 管理员能查询订单详情、填写快递公司和单号发货；会员只能读取本人的订单列表和订单详情，详情包含金额、积分抵扣、收货和物流信息。
5. 未发货完成、重复发货、已退款发货均被拒绝；重复完成不会重复发放可用积分、成长积分或积分流水。
6. 未登录、角色错配、跨会员支付单/退款访问、非法分页、非法数量、积分不足、下架商品、空物流字段和未知订单都返回预期 HTTP 错误及统一响应结构。
7. 两个并发发货请求仅一个成功；两个并发完成请求不会重复奖励。既有测试还验证了支付超时、重复支付、积分预占、退款和订单号并发。
8. 商城首页分页读取并展示全部已上架商品，卡片仅提供“查看详情”；商品详情页才提供“立即购买”。结算页默认尝试使用积分，并用服务端试算展示商品金额、积分抵扣和实付金额。
9. 商城订单列表仅展示可点击卡片，不直接提供退款按钮；详情页展示订单号、商品、收货及物流信息、费用明细，并提供取消订单和联系商家操作，视觉层级与房间订单保持一致。
10. 商城支付成功后以支付单号、订单 ID、订单号向服务端二次核验，再显示“购买成功”、订单号、“查看订单”和“返回首页”；订单号同时在支付回包、会员商城订单和管理员订单详情中断言一致。

## 风险分析与覆盖缺口

### 高风险：预支付缺少购买意图幂等性

`POST /api/app/mall/payments` 的请求体没有 `request_no`/`idempotency_key`，服务端每次调用均生成新的随机 `payment_no`。因此当前仅保证**同一支付单**重复 `mock-pay` 时幂等，无法保证网络重试或客户端重提交同一购买意图时只产生一笔待支付单/订单。该结论来自请求 DTO、服务实现和数据库约束的代码审查；它不能通过前端按钮禁用替代。应先确认契约并新增稳定幂等键、唯一约束与并发回归测试。

### 高风险：真实微信渠道未验收

未提供商户配置、真实签名、真实付款人、退款资金流和公网回调条件；因此没有执行真实微信预支付、异步通知、退款通知、渠道查询/关单异常恢复。现有微信相关单测与模拟支付通过，不能等同于真实资金流通过。

### 中风险：契约仍待确认

商城接口文档标注为“草案/实现中”，实施方案标注为“待审阅”；本次已将会员订单详情端点同步到接口草案，但方案列出的 `/api/app/mall/address`、退款查询端点仍与当前代码/接口草案不一致。上线前应指定唯一生效的需求、接口和数据库基线。

### 其他覆盖缺口

- 未执行微信开发者工具/真机交互测试，只执行了小程序 TypeScript 检查和页面逻辑审查。
- 未执行性能、容量、恶意重放和长时任务稳定性测试。
- 商品下架与预支付提交的跨事务竞态、以及真实微信退款与发货竞争，需要在确认业务规则后补充 MySQL 并发测试。
