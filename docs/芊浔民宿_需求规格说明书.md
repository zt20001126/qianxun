# 芊浔民宿微信小程序及管理后台需求规格说明书

> 版本：V1.2（2026-11-17）  
> 适用范围：第一期产品需求与后续数据库、接口、UI、测试设计

## 1. 项目概述

芊浔民宿位于浙江省湖州市南浔区，单店经营，共六间房：一楼 101、102、103；二楼 201、202、203。建设微信小程序供顾客直接预订并支付，建设 PC 管理后台统一管理小程序及第三方平台订单、房态、会员积分、达人费用和经营报表。

**第一期原则**：以预订与管理闭环、数据准确和低维护成本为优先；不做多门店、复杂营销、动态定价及第三方平台自动对接。

### 1.1 用户角色

- **顾客/会员**：通过微信小程序注册登录、查询客房、预订支付、取消退款、查询订单、使用积分。
- **管理员**：单个后台账号；管理房间、订单、入住退房、会员积分、平台达人、经营支出与报表。

### 1.2 系统组成

微信小程序、PC 管理后台、统一后端服务及统一数据库。小程序支付成功后的订单自动进入后台，不需要二次录入。

## 2. 统一术语与订单来源

### 2.1 术语

| 名称 | 定义 |
|---|---|
| 注册账号 | 顾客登录小程序的账号 |
| 注册手机号 | 注册账号绑定且经过验证的手机号，自动积分归属依据 |
| 预订人 | 预订页面填写的联系人姓名 |
| 手机号码/预订手机号 | 预订页面填写的联系人电话，允许与注册手机号不同 |
| 入住人数 | 计划入住人数 |
| 入住人 | 实际办理入住的人员，可与预订人不同 |
| 订单金额 | 订单原始房费，创建后保留快照 |
| 顾客实付金额 | 顾客实际承担的房费 |
| 微信实付金额 | 小程序订单通过微信实际支付金额 |
| 已核收入 | 已办理入住订单对应的内部经营确认收入，不等同银行到账或会计收入 |
| 待核收入 | 尚未办理入住订单对应的预计收入 |
| 间夜 | 一间客房实际住宿一个夜晚 |

**禁止混用注册手机号、预订手机号和入住人手机号。** 小程序订单自动积分发放给下单注册账号，而非预订人或入住人。

## 3. 微信小程序需求（六个模块）

### 3.1 首页与房间查询

- 首页展示品牌信息和预订卡片：**入住日期、退房日期、共几晚、查询按钮**。
- 退房日期必须晚于入住日期；不允许选择过去的入住日期；自动计算晚数。
- 查询整个住宿区间内可订房间；有效订单、管理员封房及有效支付临时占用均不可重复预订。
- 支持不选日期直接浏览全部房间；不做复杂筛选、排序和入住人数搜索。

### 3.2 房间详情与可订日历

- 展示房间号、房型、楼层、图片、面积、床型、可入住人数、设施、介绍及每晚价格。
- 日期日历标识可订与不可订；修改日期重新计算晚数和费用。
- 每间房第一期仅一个基础房价；不做周末、节假日和动态定价。
- 房价变更仅影响新订单，历史订单保存价格快照。

### 3.3 预订与微信支付

预订填写页字段**统一命名**如下：

| 字段 | 必填 | 说明 |
|---|---|---|
| 预订人 | 是 | 联系人姓名，不等同于注册账号或实际入住人 |
| 手机号码 | 是 | 预订联系人电话 |
| 入住人数 | 是 | 不超过客房容量 |
| 备注 | 否 | 特殊需求 |

不要求预订页面填写身份证号码；实际住宿登记信息可由管理员依法按需补充。

- 费用展示：房费原价、积分抵扣金额、微信实付金额；微信实付 = 房费原价 − 积分抵扣。
- 下单时后端再次校验库存、价格、会员积分；创建**临时支付交易**并短时间锁定对应间夜。
- **只有支付成功且经后端核实后才创建正式订单**，初始状态「待确认」，自动出现在 PC 后台。
- 支付失败、取消或超时不创建正式订单；临时占用到期释放。
- 处理支付回调重复、延迟、异常和并发抢房；不得仅依赖前端支付成功提示。
- 第一阶段一笔订单只预订一间房，不做多房间合单。

### 3.4 我的订单与退款

正式订单状态：**待确认、待入住、已入住、已完成、已取消**。不设置可见的正式「待支付」订单。

- 列表展示订单号、房间、入住日期、住宿晚数、实付金额、状态。
- **待确认或待入住**订单，且当前时间**严格早于入住当天 18:00（北京时间）**，允许顾客自助取消并申请退款。
- 当天 18:00 起不支持普通自助退款；18:00 之后新下单也没有额外宽限期。
- 已入住、已完成订单不提供普通退款入口；重复扣款、商家无法履约或依法需要处理的情况走异常处理。
- 微信退款按原支付渠道处理；退款状态、流水、失败原因独立保存，订单原始金额不修改。
- 取消订单须处理已抵扣积分的退回，并以可靠状态和幂等逻辑避免重复退款、重复返积分。
- 第一期不支持已付款订单修改房间、入住日期、退房日期和金额；符合退款条件时可取消后重订。

### 3.5 会员与积分

#### 会员等级

| 等级 | 累计获得积分门槛 |
|---|---:|
| 普通会员 | 0–499 |
| 银卡会员 | 500–999 |
| 金卡会员 | 1000–1499 |
| 钻石会员 | ≥1500 |

新注册用户为普通会员。等级依据累计成长积分判定，消费可用积分不降低等级；积分不设有效期。

#### 自动发放

- 小程序订单变为「已完成」（办理退房）后，按**微信实际支付金额每满 ¥1 发 1 积分**；小数金额建议向下取整。
- **积分归属订单关联的小程序注册账号**，由账号确定绑定手机号；不以预订人/入住人手机号匹配。
- 一笔订单正常自动奖励仅发一次；失败记录原因，支持安全重试；需要唯一约束或幂等标识。
- 外部平台手动订单不自动绑定小程序会员，也不自动按预订手机号发积分。

#### 管理员手动发放

- 管理员输入**会员手机号**查询账号，填写发放积分数量并确认，即可发放；建议提供可选备注/原因及关联订单。
- 会员不存在时提示，不自动创建未验证账号。
- 记录管理员、手机号对应会员、数量、时间、原因、关联订单、变动前后余额，防止重复提交。
- **建议**区分「历史消费补发」（计入累计成长积分）与「赠送/补偿」（仅增加可用积分）；此项尚待最终确认。

#### 积分抵扣

- 单笔订单抵扣上限为**房费的 20%**；同时不得超过可用积分可兑换金额。
- 暂定兑换率：普通 30、银卡 25、金卡 20、钻石 15 积分抵扣 ¥1，**尚未最终确认**。
- 订单取消退款时恢复已实际扣除的积分；支付失败或临时交易超时释放预占积分。
- 积分流水包括订单奖励、人工发放、抵扣、返还、异常调整，记录来源及关联业务。

### 3.6 个人中心

展示昵称、会员等级、累计成长积分、可用积分、我的订单、积分流水、民宿地址与联系电话；个人资料页面保持简洁。

## 4. PC 管理后台需求（九个模块）

### 4.1 今日经营总览

- 显示今日客房占用、今日已核营业额、今日待核营业额、今日平台手续费、今日达人提成、今日净营业额。
- 六间房状态卡片展示房号、房态、预订人、入住人数、入住/退房日期、订单来源；点击进入订单。
- **今日住宿收入按今天对应的住宿夜晚归属**，不是按今日创建订单或今日收款计算。
- 已核与待核须分开，实际到账/结算也应与经营收入分开。

### 4.2 月度房态日历

六种正式房态：

| 房态 | 业务含义 |
|---|---|
| 空房 | 当晚可预订 |
| 已预订 | 已支付，管理员尚未确认（订单待确认） |
| 待入住 | 管理员已确认 |
| 已入住 | 已办理入住 |
| 已退房 | 已办理退房（订单已完成） |
| 不可预订 | 管理员封房 |

**展示规则（已确认）：**

- 六间房为行、日期为列，每个住宿夜晚一个格子。
- **入住日期格子显示完整订单状态**；连住的后续夜晚显示「占用」，仅为视觉标记，**不是第七种正式房态**。
- 退房日期不占用当晚，可显示空房或该晚新订单状态。
- 办理退房后，原入住日期格子显示「已退房」，续住夜晚仍显示「占用」作为历史记录。
- 点击入住日状态或续住「占用」格子均可查看同一笔订单。
- 例如 11/17 入住、11/20 退房：17 日「已入住」、18–19 日「占用」、20 日「空房」；退房后 17 日改为「已退房」。
- 后端始终按整个 `[入住日期, 退房日期)` 区间判断冲突，不依据格子文案判断。
- 支持切换月份、查看来源和封房记录。

### 4.3 订单管理

- 七种来源统一列表，支持按来源、房间、状态、日期、预订人、手机号筛选。
- 列表建议展示房间、来源、预订人、手机号、入住人数、入住/退房日期、晚数、订单金额、实付、各项费用、净营业额、状态。
- 系统订单号、平台订单号可保存，列表默认隐藏，详情中可查。
- **小程序订单**支付成功自动进入后台，初始「待确认」；管理员确认后「待入住」，办理入住后「已入住」，办理退房后「已完成」。
- **外部平台订单**管理员手动录入，初始「待入住」，录入时必须校验房态并立即占用住宿夜晚。
- 外部订单录入字段：来源、房间、入住/退房日期、预订人、手机号、入住人数、订单房费、顾客实付、平台手续费、平台达人提成、额外达人提成、平台实际结算金额、备注；建议保存平台订单号防重。
- 原始成交金额及价格快照不直接修改；第一期不支持改期换房；允许按规则更正联系人、入住资料及备注并保留操作日志。
- 支付记录和退款记录独立查询，不把外部平台订单伪装成微信支付流水。

### 4.4 客房管理

- 管理六间房的房号、名称、楼层、图片、面积、床型、人数、设施、介绍和基础价格。
- 支持指定日期范围封房；与有效订单冲突时拒绝直接封房并提示先处理订单。
- 调整价格不追溯影响已有订单。

### 4.5 顾客与会员管理

- 顾客资料与会员账号分离：实际入住人可记录姓名、手机号、年龄及依法必要的住宿登记资料；一笔订单可关联多位入住人。
- 会员按注册手机号检索，展示等级、累计成长积分、可用积分、订单与流水。
- 管理员通过手机号手动发放积分，记录操作日志和发放原因；自动发放失败可查询和重试。
- 小程序订单积分归属注册账号；外部订单不因预订手机号相同而自动发积分。

### 4.6 平台与达人管理

- 固定七种订单来源；支持按平台统计订单数、间夜、顾客实付、手续费、佣金及净营业额。
- 达人资料包括名称、所属平台及关联订单；统计达人订单数、间夜数、成交额、平台达人提成和额外达人提成。
- 外部订单金额区分：顾客实付房费、平台手续费、平台达人提成、民宿额外达人提成、平台实际结算金额、最终净营业额。
- **不得重复扣除已包含在平台费用中的达人佣金。** 平台实际结算以平台账单为准，可能存在平台补贴或优惠差异。
- 小程序订单记录房费、积分抵扣、微信实付；不要求人工填写第三方平台手续费或达人佣金。微信支付可能有商户手续费，第一期可暂不逐笔人工录入。

### 4.7 经营支出管理

- CRUD：新增、查询、编辑、删除、统计。
- 字段：ID、支出内容（自由填写）、支出金额、支出日期、创建时间、更新时间。
- 不强制支出类型；房租、水电、采购、人工、维修等自行填写。
- 与订单独立记录，但纳入经营利润。

### 4.8 经营报表

支持整体、按平台、按达人、按房间、按日、按月统计：订单数、间夜数、已核营业额、待核营业额、平台手续费、达人提成、净营业额、经营支出、经营利润。

- **按住宿夜晚归属收入**：11/17 入住、11/19 退房，¥200/晚，17 日和 18 日各计 ¥200，19 日不计。
- **跨月分摊**：11/30 入住、12/2 退房，共 ¥400，则 11 月 ¥200、12 月 ¥200。
- 平台手续费及达人提成按住宿夜晚合理分摊；订单办理入住后内部状态整体转已核，但每晚仍按日期归属。
- **净营业额 = 有效房费收入 − 平台手续费 − 平台达人提成 − 民宿额外达人提成**。
- **经营利润 = 净营业额 − 经营支出**；第一期不强制把公共费用分摊到房间。
- 小程序积分抵扣减少顾客实际支付，报表须区分房费原价、抵扣与实付；避免把积分抵扣当成现金收入。
- 退款、优惠、平台补贴和异常调整须保留独立记录，不通过覆盖历史订单金额处理。

### 4.9 系统设置

单管理员登录及修改密码、民宿名称/地址/电话、微信支付配置、退款规则、积分兑换参数、20% 抵扣上限、必要操作日志和数据备份。

## 5. 核心流程

### 5.1 小程序订单

注册登录 → 查询房间 → 选择日期与房间 → 填写**预订人/手机号码/入住人数/备注** → 选择积分抵扣 → 确认费用 → 临时锁房并发起微信支付 → 后端确认支付成功 → 正式订单自动入后台（待确认）→ 管理员确认（待入住）→ 办理入住（已入住）→ 办理退房（已完成）→ **向下单注册账号发放积分**。

### 5.2 外部订单

第三方平台产生订单 → 管理员手动录入 → 校验房态 → 创建待入住订单 → 办理入住 → 办理退房 → 如有需要，管理员通过会员手机号手动发放积分。

### 5.3 取消退款

顾客打开待确认/待入住订单 → 校验北京时间入住当日 18:00 截止 → 申请取消退款 → 记录取消/退款状态 → 原渠道退款 → 返还已使用积分 → 更新库存与流水；异常或失败须可追踪、可重试且不得重复执行。

### 5.4 手动积分发放

管理员进入会员管理 → 输入注册手机号 → 查询会员 → 输入积分数量 → 确认 → 更新余额及积分流水 → 记录操作人、原因和时间。建议提供「历史消费补发」与「赠送/补偿」原因分类。

## 6. 核心数据对象与设计约束

| 对象 | 作用 |
|---|---|
| 注册账号 | 微信登录身份、验证手机号 |
| 会员 | 等级、累计成长积分、可用积分 |
| 房间 | 基础资料、价格 |
| 封房记录 | 不可订日期区间 |
| 正式订单 | 七种渠道统一订单、状态、注册账号关联、预订人快照 |
| 订单间夜明细 | 每晚价格、收入归属及跨月分摊 |
| 临时支付交易 | 预支付锁房及超时控制 |
| 支付记录 | 微信支付交易与回调 |
| 退款记录 | 退款状态、流水、原因 |
| 入住人/订单入住人 | 实际住宿登记，区别于预订人 |
| 积分流水 | 自动发放、手动发放、抵扣、返还及调整 |
| 积分发放任务 | 失败原因、重试、幂等 |
| 订单来源 | 七种固定渠道 |
| 达人 | 所属平台及佣金关联 |
| 经营支出 | 内容、金额、支出日期 |
| 管理员/操作日志 | 单账号管理及关键变更审计 |

**关键约束：**

1. 预订区间采用 `[入住日, 退房日)`，退房当晚可售。
2. 防止同一房间同一住宿夜晚出现两笔有效订单或有效锁房冲突。
3. 支付回调、退款、积分发放、人工积分发放均需幂等处理。
4. 订单金额、每晚价格及手续费保存快照；财务调整另记流水。
5. 注册账号、预订联系人和实际入住人是不同业务实体。
6. 外部订单不生成虚假的微信支付流水。
7. 重要操作留痕；敏感手机号、住宿登记信息依法保护；数据库定期备份。

## 7. 第一阶段明确不开发

第三方平台 API 自动同步；已付款订单改期/换房/补差价；多房间合单；多门店；多管理员复杂权限；周末/节假日/动态价格；复杂优惠券、拼团、满减；积分过期；外部订单自动认领会员；已完成订单普通退款；完整财务会计系统；员工排班和库存系统。

## 8. 开发顺序

1. **房间与订单基础**：房间、价格、封房、统一订单、手动录入、状态流转、房态日历。
2. **小程序预订支付**：注册登录、查询、详情、预订表单、微信支付、自动入后台、退款。
3. **会员积分**：等级、自动发放、手机号手动发放、抵扣、流水、失败重试。
4. **经营管理与报表**：平台达人、支出、今日总览、跨月间夜统计、净营业额和利润。

财务快照、间夜明细、支付退款和积分流水的数据结构必须在前期规划，避免后续返工。

## 9. 验收标准

- [ ] 六间房均可管理、查询、预订，日期冲突被阻止。
- [ ] 小程序支付成功自动生成一笔后台正式订单；支付失败不生成。
- [ ] 六种外部来源均可手动录入，默认待入住。
- [ ] 订单状态按待确认→待入住→已入住→已完成流转。
- [ ] 房态日历显示六种正式房态，连住后续夜晚显示「占用」，退房当晚可售。
- [ ] 预订表单仅要求预订人、手机号码、入住人数，备注可选。
- [ ] 退款严格执行待确认/待入住且入住当日 18:00 前的规则。
- [ ] 小程序自动积分归属**下单注册账号**，即使预订手机号不同也不会发错。
- [ ] 管理员可通过手机号查询会员并手动发放积分，留存流水。
- [ ] 同一订单自动积分不重复，失败可重试。
- [ ] 等级门槛为 500/1000/1500，积分抵扣上限 20%。
- [ ] 第三方订单手续费、达人佣金及实际结算记录清晰，不重复扣费。
- [ ] 每日收入按住宿夜晚归属，跨月正确拆分。
- [ ] 经营支出独立记录，并纳入经营利润。

## 10. 待最终确认事项

1. **积分兑换率**：普通/银卡/金卡/钻石分别 30/25/20/15 积分抵扣 ¥1，目前仍为建议值。
2. **人工积分与升级关系**：建议历史消费补发计入累计成长积分，赠送/补偿仅增加可用余额；待确认。
3. **外部平台补贴/商家优惠**：出现顾客实付与平台结算不一致时，需要明确补贴承担方及收入归属。
4. **异常退款**：已完成订单不提供普通退款入口，但需要保留依法退款和支付差错处理能力。
5. **支付手续费对账**：微信支付商户手续费第一期可不逐笔人工录入，后续对账完善。
6. **人工外部订单重复录入**：建议以平台+平台订单号防重，并提供冲突提示。
