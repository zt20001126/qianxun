# 芊浔民宿微信小程序及管理后台需求规格说明书

> 版本：V3.1（2026-11-18）  
> 适用范围：第一期产品需求与后续数据库、接口、UI、测试设计

## 1. 项目概述

芊浔民宿位于浙江省湖州市南浔区，单店经营，共六间房：一楼 101、102、103；二楼 201、202、203。建设微信小程序供顾客直接预订并完成模拟支付（第一期不接入真实微信支付），建设 PC 管理后台统一管理小程序及第三方平台订单、房态、会员积分、达人费用和经营报表。

**第一期原则**：以预订与管理闭环、数据准确和低维护成本为优先；不做多门店、复杂营销、动态定价及第三方平台自动对接。

### 1.1 用户角色

- **顾客/会员**：通过微信小程序直接输入手机号登录、查询客房、预订并模拟支付、取消退款、查询订单、使用积分。
- **管理员**：单个后台账号；管理房间、订单、入住退房、会员积分、平台达人、经营支出与报表。

### 1.2 系统组成

微信小程序、PC 管理后台、统一后端服务及统一数据库。小程序支付成功后的订单自动进入后台，不需要二次录入。

## 3. 微信小程序需求（七个模块）

### 3.1 手机号登录、首页与房间查询

- 顾客输入手机号并点击登录；第一期不使用短信验证码、微信手机号授权、微信 OpenID 或注册页面。后端按 `members.phone` 查找会员，存在则直接登录，不存在则自动创建；手机号必须校验格式，明确提示此方案不能验证手机号归属、存在冒用账号及积分的风险。
- 登录成功签发 JWT，有效期 **30 天**；小程序本地保存并在有效期内自动登录，过期重新输入手机号。不提供 Refresh Token。
- 所有会员使用统一默认头像，昵称固定为手机号后四位；已有会员首次登录时覆盖原昵称，第一期用户不能修改昵称或头像。

- 首页展示品牌信息和预订卡片：**入住日期、退房日期、共几晚、查询按钮**。
- 退房日期必须晚于入住日期；不允许选择过去的入住日期；自动计算晚数。
- 查询整个住宿区间内可订房间；有效订单、管理员封房及有效支付临时占用均不可重复预订。
- 支持不选日期直接浏览全部房间；不做复杂筛选、排序和入住人数搜索。
- 查询结果逐间展示房间缩略图、房间名称、床型等基本信息、可入住人数、每晚价格及「查看详情」按钮。查询结果必须满足整个所选住宿区间可订。

### 3.2 房间详情与可订日历

- 展示房间号、房型、楼层、图片、面积、床型、可入住人数、设施、介绍及每晚价格。
- 房间详情展示底部「立即预订」按钮，点击后进入入住日期选择日历。
- 小程序日历只显示「可预订」「不可预订」两种状态，不展示订单详情、后台房态或不可订原因；已有有效订单、有效临时锁房或管理员封房覆盖的住宿夜晚均不可选。
- 日期范围：按北京时间从今天起**连续 60 个自然日**（今天为第 1 天）供选择；入住和退房日期都必须位于此范围内，且退房日期晚于入住日期。前后端同时校验。其他平台订单须先由管理员录入系统才能反映为不可订。
- 修改日期重新计算晚数和费用，确认入住及退房日期后进入预订填写页。
- 每间房第一期仅一个基础房价；不做周末、节假日和动态定价。
- 房价变更仅影响新订单，历史订单保存价格快照。

### 3.3 预订与模拟支付（第一期）

预订填写页字段**统一命名**如下：

| 字段 | 必填 | 说明 |
|---|---|---|
| 预订人 | 是 | 联系人姓名，不等同于注册账号或实际入住人 |
| 手机号码 | 是 | 预订联系人电话 |
| 入住人数 | 是 | 不超过客房容量 |
| 备注 | 否 | 特殊需求 |

不要求预订页面填写身份证号码；实际住宿登记信息可由管理员依法按需补充。

- 预订填写页顶部展示房间缩略图、房间名称、入住/退房日期及住宿晚数；表单字段为预订人、手机号码、入住人数、备注。
- 费用展示：基础房价 × 晚数、房费原价/总价、使用积分数量、积分抵扣金额、模拟实付金额；模拟实付 = 房费原价 − 积分抵扣。
- 页面底部显示「立即支付」按钮；第一期调用**后端模拟支付成功接口**，不调用微信支付、不收取真实款项、不获取 OpenID。模拟成功后正常生成支付记录和正式订单。
- 下单时后端再次校验库存、价格、会员积分；创建**临时支付交易**并锁定对应间夜 **10 分钟**，在 `booking_lock` 和 `payments` 中保存交易数据。
- **只有服务端模拟支付成功后才创建正式订单**，初始状态「待确认」，自动出现在 PC 后台；`payments.amount` 必须等于后端计算的积分抵扣后实际应付金额，不能相信客户端传入金额。
- 支付失败、取消或超时不创建正式订单。支付前冻结抵扣积分，支付成功才扣除，失败或支付交易确认关闭后解冻。
- 锁房到期后由后端事务确认模拟支付是否已成功；仍未成功的交易置为 `CLOSED`、锁房置为 `EXPIRED`，然后释放间夜与冻结积分。模拟支付与超时关闭必须串行化/幂等，防止超时后仍生成冲突订单。**将来接入真实微信支付时**，才需要先查询微信交易状态并确认关单成功再释放。
- 已创建且仍有效的待支付交易保留原房价；管理员修改基础价格只影响后续新创建交易。
- 处理重复点击支付、请求重试、超时关闭和并发抢房；不得仅依赖前端支付成功提示。第一期没有微信支付回调。
- 第一阶段一笔订单只预订一间房，不做多房间合单。
- 后端模拟支付成功后进入「预订成功」结果页，显示「查看订单」「返回首页」两个按钮；支付未核实成功时不可错误展示预订成功。

### 3.4 我的订单与退款

正式订单状态：**待确认、待入住、已入住、已完成、已取消**。不设置可见的正式「待支付」订单。

- 我的订单页面第一期**只显示「全部订单」**入口/列表；列表中的订单可展示状态，但不提供六个状态筛选标签。
- 列表卡片只展示**订单号、入住日期、住宿晚数、实付金额**；状态与房间等详细信息在订单详情中展示。
- 点击订单进入详情：顶部展示订单状态；订单信息包括订单号、房间、入住日期、退房日期、住宿晚数、入住人数、预订人、手机号码、备注；费用明细展示每晚房价 × 晚数（或逐晚明细）、房费总价、使用积分数、积分抵扣金额、实付金额。
- **待确认或待入住**订单，且当前时间**严格早于入住当天 18:00（北京时间）**，允许顾客自助取消并申请退款。
- 当天 18:00 起不支持普通自助退款；18:00 之后新下单也没有额外宽限期。
- 已入住、已完成订单不支持常规退款；**已完成订单不支持取消**，后台和小程序均不得将其作为普通取消/退款操作处理。依法必须处理的支付差错或争议不属于普通订单退款流程。
- 第一期执行**模拟退款**：校验通过后后端同步写入 `refunds` 成功流水（退款金额等于该笔模拟支付实付金额），并将订单标记已取消、返还抵扣积分、释放原定间夜；不发生真实资金流转。保留退款状态、流水及失败原因，订单原始金额不修改。后续真实微信退款必须待真实退款成功才释放。
- 取消退款成功后须处理已抵扣积分的退回，并以可靠状态和幂等逻辑避免重复退款、重复返积分。
- 顾客端不提供已付款订单改期、换房或改价；管理员可在「待确认」「待入住」阶段修改房间或住宿日期，但**住宿晚数必须不变**，且完整区间重新校验冲突。
- **所有来源、所有状态的订单创建后金额和三类费用均不可编辑**。所有状态（包括已取消）的预订人、手机号、入住人数、实际入住人及备注等基本资料可由管理员修改；「已入住」「已完成」「已取消」不得改房间或日期。
- 订单详情底部仅展示「取消订单」入口：符合自助退款条件时可操作；不符合时显示灰色不可直接提交退款的样式，点击提示「当前订单不支持自助退款，请联系商家」，并展示商家联系电话。前后端均必须重新校验资格；已完成订单不开放取消或退款操作；依法必须处理的支付差错或争议另行处理。

### 3.5 会员与积分

#### 会员等级

| 等级 | 累计获得积分门槛 |
|---|---:|
| 普通会员 | 0–499 |
| 银卡会员 | 500–999 |
| 金卡会员 | 1000–1499 |
| 钻石会员 | ≥1500 |

新注册用户为普通会员。等级依据累计成长积分判定，消费可用积分不降低等级；积分不设有效期。

#### 自动发放

- 小程序订单变为「已完成」（办理退房）后，按**模拟实付金额每满 ¥1 发 1 积分**；小数金额建议向下取整。
- **积分归属订单关联的小程序注册账号**，由账号确定绑定手机号；不以预订人/入住人手机号匹配。
- 一笔订单正常自动奖励仅发一次；失败记录原因，支持安全重试；需要唯一约束或幂等标识。
- **第三方订单仅在「已完成」且有有效预订手机号时自动创建或关联会员，并按实付金额每满 ¥1 奖励 1 积分**（不足 ¥1 不计）。未完成第三方订单不自动创建会员或发放积分。
- 管理员手动录入初始状态为「已完成」的历史第三方订单，保存成功后立即按上述规则创建/关联会员并发放积分；没有有效手机号时可保存订单，但不创建会员或发积分。
- 同一手机号会员去重、同一订单积分仅发一次；发放时保存金额和积分流水快照。
- 已完成第三方订单原先没有手机号，管理员后来补录有效手机号时，若从未奖励则自动奖励一次；已经奖励的订单即使后来修改手机号，也不转移、不追回、不补发积分。

#### 管理员手动发放

- 管理员输入**会员手机号**查询账号，填写发放积分数量并确认，即可发放；建议提供可选备注/原因及关联订单。
- 会员管理支持单独新增会员、录入初始积分；不要求会员已经登录小程序。顾客以后直接输入相同手机号登录后关联既有会员。
- 记录手机号对应会员、数量、时间、原因、关联订单及**变动后可用积分余额 `balance_after`**，防止重复提交；第一期积分流水不增加 `admin_id`、`balance_before`。
- **已确认**：「历史消费补发积分」同时计入累计成长积分与可用积分，参与等级升级；「赠送/补偿积分」仅增加可用积分，不增加累计成长积分，不影响会员等级。发放时必须选择类型并记录流水。

#### 积分抵扣

- 积分使用数量必须为非负整数；抵扣金额按 `floor(points_used / 当前等级兑换率 × 100) / 100` 计算，即人民币向下取整到分；不使用浮点计算。例：普通会员 1 积分抵扣 ¥0.03，15 积分抵扣 ¥0.50。
- 单笔订单抵扣上限为**房费的 20%**；同时不得超过可用积分可兑换金额。
- **已确认兑换率**：普通会员 30 积分抵扣 ¥1、银卡会员 25 积分抵扣 ¥1、金卡会员 20 积分抵扣 ¥1、钻石会员 15 积分抵扣 ¥1。
- 订单取消退款时恢复已实际扣除的积分；支付失败或临时交易超时释放预占积分。
- 积分流水包括订单奖励、人工发放、抵扣、返还、异常调整，记录来源、关联业务及变动后余额 `balance_after`；会员余额更新与流水写入必须在同一数据库事务完成。

### 3.6 会员中心（已确认独立页面）

- 需要独立会员中心页面，展示当前会员等级、累计成长积分、可用积分、距离下一等级所需成长积分及升级进度；钻石等级显示已达最高等级。
- 展示四个等级的成长积分门槛及**已确认**的积分兑换比例；展示积分获取、抵扣上限、取消订单返还、积分无有效期等规则。
- 提供「积分流水」入口，支持查看积分获取、使用、返还及管理员发放记录，展示时间、变动积分和来源。
- 不新增优先入住、专属客服、活动通知、优惠券等未经确认的会员权益。
- **已确认**：第一期会员中心作为微信小程序底部导航栏的独立入口。

### 3.7 个人中心

展示统一默认头像、手机号后四位昵称、会员等级、累计成长积分、可用积分、我的订单、会员中心入口、积分流水、民宿地址与联系电话；个人资料页面保持简洁。

## 4. PC 管理后台需求（九个模块）

### 4.1 经营总览（可切换月份）

- 支持切换月份查看经营数据；当日客房占用与所选月份经营指标应明确标注时间口径。展示「未入住订单营业额」「已入住订单营业额」、平台手续费、平台达人提成、达人额外提成、到手金额和净利润。
- 六间房状态卡片展示房号、房态、预订人、入住人数、入住/退房日期、订单来源；点击进入订单。
- **今日住宿收入按今天对应的住宿夜晚归属**，不是按今日创建订单或今日收款计算。
- 未入住与已入住订单营业额须分开；实际到账/结算与经营营业额分开。

### 4.2 月度房态日历

六种正式房态：

| 房态 | 业务含义 |
|---|---|
| 空房 | 当晚可预订 |
| 已预订 | 已支付，管理员尚未确认（订单待确认） |
| 待入住 | 管理员已确认 |
| 已入住 | 已办理入住 |
| 已退房 | 已办理退房（订单已完成） |
| 不可预订 | 管理员封房 |

**展示规则（已确认）：**

- 六间房为行、日期为列，每个住宿夜晚一个格子。
- **入住日期格子显示完整订单状态**；连住的后续夜晚显示「占用」，仅为视觉标记，**不是第七种正式房态**。
- 退房日期不占用当晚，可显示空房或该晚新订单状态。
- 办理退房后，原入住日期格子显示「已退房」，续住夜晚仍显示「占用」作为历史记录。
- 点击入住日状态或续住「占用」格子均可查看同一笔订单。
- 例如 11/17 入住、11/20 退房：17 日「已入住」、18–19 日「占用」、20 日「空房」；退房后 17 日改为「已退房」。
- 后端始终按整个 `[入住日期, 退房日期)` 区间判断冲突，不依据格子文案判断。
- 支持切换月份、查看来源和封房记录。
- 订单超过预定入住日期仍未到店，不自动取消，保持待入住并继续占用其**原定住宿间夜**；管理员后续处理。
- 订单超过预定退房日期但尚未人工办理退房，原定退房日期及之后仍可预订；同一房间允许前单退房日当天新单入住。房态冲突以日期区间为准，不以管理员是否点击退房为准。
- 管理员封房只允许覆盖无有效订单/有效锁房的可订间夜；遇已封日期需先手动解除封房才可录入第三方订单；支持调整封房区间、全部或部分解除。
- 后台房态日历**不展示待支付临时锁房状态**；其格子可能暂显示空房，但点击录单提交时后端必须复核有效锁房并拒绝冲突，不允许超售。
- **点击空房格子可新增第三方订单**：自动带入房间号、入住日期，退房日期默认次日；住多晚时可修改退房日期。提交时重新检查完整日期区间的房态冲突。

### 4.3 订单管理

- 七种来源统一管理，支持来源、房间、状态、日期、预订人、手机号筛选；第三方订单仅支持管理员逐笔手动录入。
- 订单管理新增时手动选择房间和入住/退房日期；从房态日历点击空房格子新增时自动带入房间号和入住日期，退房日期默认次日且可修改；两种入口复用同一订单创建逻辑。
- 小程序订单模拟支付成功自动入后台，初始「待确认」，必须由管理员手动确认；不提供管理员拒绝已支付小程序订单功能。
- 正常订单状态只允许逐级前进：待确认→待入住→已入住→已完成；不得跳级或倒退。入住操作不得早于预定入住日，退房操作不得早于预定退房日；退房须管理员手动操作，不因到期自动完成。
- 第三方订单创建时可直接选择「待确认」「待入住」「已入住」「已完成」四种初始状态，不可直接创建「已取消」；后续同样只允许逐级前进。
- **第三方订单字段如下**：

| 字段 | 要求 |
|---|---|
| 订单来源 | 必填：抖音、美团、携程、同程、飞猪、途家 |
| 房间号、入住日期、退房日期 | 必填；日历入口自动带入房号、入住日，退房日默认次日 |
| 订单状态 | 必填；允许手动录入历史已完成订单 |
| **实付金额** | **必填；顾客实际支付金额** |
| 平台手续费 | 选填，默认 0 |
| 平台达人提成 | 选填，默认 0 |
| 达人额外提成 | 系统自动计算，无主播时为 0 |
| 预期收入 | 有主播时必填，计算额外提成使用；无主播时为空 |
| **净营业额** | 自动计算，不手填 |
| 预订人、手机号、入住人数、备注 | 选填；手机号用于完成订单的会员积分 |
| 平台订单号、关联达人 | 选填；建议提供平台订单号防重 |

- **不再要求输入订单原始房费，也不强制填写平台实际结算金额。**
- **净营业额 = 实付金额 − 平台手续费 − 平台达人提成 − 达人额外提成**。避免同一费用重复扣除。
- 订单创建后实付金额、平台手续费、平台达人提成、额外提成、预期收入均不可修改。第三方订单在入住前发现价格录错，可取消原订单并重新录入；取消原因选填。
- 待确认、待入住订单允许管理员改房间或日期，但住宿晚数不得变化；日期变动后相关月份的收入及费用分摊自动重算。所有订单状态均可编辑预订人、手机号、入住人数、实际入住人、备注等基本资料；已入住、已完成、已取消不可改房间或日期。
- 第三方待确认/待入住订单可由管理员直接取消并立即释放原定间夜；退款由第三方平台自行处理。第一期小程序模拟退款**同步成功**后，将订单标记已取消、返还已抵扣积分并释放间夜；模拟退款处理异常时不得提前释放或重复返积分。真实支付接入后须以真实退款成功为前提。
- **已发积分不追回、不补发、不重新计算**；同一订单不能因修改或重复提交而再次发积分。
- 手动保存前校验日期、金额、房态冲突及重复订单；有平台订单号时以来源+平台订单号防重。历史订单如与已有有效订单或封房冲突，系统提示并拒绝保存，由管理员自行调整冲突记录后重试；不得绕过占房校验。
- 小程序订单的模拟支付、退款流水与第三方订单金额录入相互独立；不因此开放小程序顾客自助改价、改期或换房。

### 4.4 客房管理

- 管理六间房的房号、名称、楼层、图片、面积、床型、人数、设施、介绍和基础价格。图片文件采用阿里云 OSS，数据库 `room.images` 存储 URL 数组；旧房间资料由本地 `homestay_db.room` 和 `homestay_db.room_type` 一次性迁移，旧图地址须核实并按需迁移文件至 OSS。
- 支持指定日期范围封房、调整封房日期、全部或部分解封；与有效订单或支付锁房冲突时拒绝封房。封房日期录入第三方订单前必须先由管理员手动解封。
- 调整价格不追溯影响已有订单。

### 4.5 会员管理

- 后台统一设置「会员管理」，不再另设独立顾客管理菜单；实际入住人登记仍可保留在订单关联资料中。
- 支持按手机号查询、单独新增会员、设置初始积分、查看等级、成长积分、可用积分、消费订单及积分流水。
- **管理员可直接创建从未登录过微信小程序的会员**；该顾客以后直接输入同一手机号时关联已有会员并查看积分。第一期不验证手机号所有权。按手机号去重，不重复创建。
- 第三方订单中预订人和手机号均为选填。只有订单已完成且手机号有效时，自动创建或关联会员并按**实付金额每满 ¥1 发 1 积分**；历史已完成订单手动录入成功后立即处理。未完成订单不自动建会员、不发积分。
- 小程序订单奖励仍归属于下单时以手机号登录的注册账号，不能仅按预订手机号发给其他人。
- 支持管理员手动赠送积分，记录来源、时间、关联订单和变动后余额（不增加积分流水 `admin_id`）；人工录入初始积分时应明确其来源类型：历史消费积分计入成长积分及可用积分；赠送/补偿仅计入可用积分。
- 同一订单仅奖励一次；发放时记录当时实付金额和积分数。已完成第三方订单后补手机号且尚未发积分时自动奖励；已奖励后修改手机号不转移积分。

### 4.6 平台与达人管理

- 固定七种订单来源；支持按平台统计订单数、间夜、顾客实付、手续费、佣金及净营业额。
- 达人资料包括名称、所属平台及关联订单；达人可不选，默认无主播。统计达人订单数、间夜数、成交额、平台达人提成、额外达人提成和总提成；报表包含「无主播订单」分组。
- 外部订单金额区分：实付金额、平台手续费、平台达人提成、达人额外提成、净营业额；平台实际结算金额不作为第一期强制录入项。
- **不得重复扣除已包含在平台费用中的达人佣金。** 平台实际结算以平台账单为准，可能存在平台补贴或优惠差异。
- 小程序订单记录房费、积分抵扣、模拟实付；不要求人工填写第三方平台手续费或达人佣金。未来真实微信支付可能有商户手续费，但**第一期不计入经营成本，也不计入平台手续费**，不要求逐笔录入。

### 4.7 经营支出管理

- 仅允许**新增、查询、统计**；记录创建后不可编辑、删除。
- 字段：ID、支出内容（自由填写）、支出金额、支出日期、创建时间、更新时间。
- 不强制支出类型；房租、水电、采购、人工、维修等自行填写。
- 与订单独立记录，但纳入经营利润。

### 4.8 经营报表

- 默认当前月份，可查询任意历史月份；不锁定历史报表，按现有订单资料动态重新计算。
- 四个维度：**经营总览、按来源、按主播、按房间**。四个维度统一支持 `全部有效订单`（默认）、`未入住订单`、`已入住订单` 筛选；取消订单均排除。
- 未入住订单 = `PENDING_CONFIRM` + `PENDING_CHECKIN`；已入住订单 = `CHECKED_IN` + `COMPLETED`。所有维度的订单数、间夜数、营业额、平台手续费、普通主播提成、额外主播提成、到手金额均随筛选条件一致变化。
- **订单数**只计入其入住日期所属月份，跨月订单不重复计数；**间夜数、营业额及三类费用**按住宿夜晚所属月份分摊，不因订单创建或付款日期改变归属。各项金额平均分摊至间夜，分币尾差归最后一晚。
- `到手金额 = 实付金额 − 平台手续费 − 普通主播提成 − 额外主播提成`；小程序积分抵扣后仅将模拟实付金额计入营业额，不按房费原价计算现金收入。
- 第一阶段报表中小程序的模拟支付金额按**业务测试金额**参与统计，**不代表实际收到现金**；正式上线收款前应清理/隔离测试数据，避免混入真实经营账目。
- **净利润**固定按 `已入住订单到手金额 − 本月经营支出` 计算，不随当前报表筛选条件变化；未入住订单营业额单独展示、不计入净利润。已办理入住的跨月订单即使部分间夜尚未发生，也按完整预订区间提前分摊至对应未来月份。
- 支出按**实际支出日期**所属月份计入总览净利润，与订单独立；房间维度的利润仅扣除该房订单平台手续费、普通和额外主播提成，**不分摊全店经营支出**。
- 来源维度包括七种渠道；主播维度必须含「无主播订单」行，普通提成、额外提成和总提成分别列示；房间维度包括六间房。
- **入住率**在经营总览和房间报表展示：分母为当月房间总间夜减去管理员手动封房间夜，分子为当月已入住/已完成订单占用的间夜（包括已办理入住订单尚未到来的后续间夜）；不计算预订占用率。封房不得与有效订单重叠。
- 第一阶段不接入真实微信支付，也不记录、不配置、不统计微信支付手续费；不建立财务结算或会计核算系统。

### 4.9 系统设置

第一期不开发数据导出、备份、复杂配置、多人权限及通用审计日志；仅保留管理员安全登录；第一期不需要微信支付参数配置，不强制建设单独系统设置页面。

## 5. 核心流程

### 5.1 小程序订单

输入手机号登录 → 查询房间 → 选择日期与房间 → 填写**预订人/手机号码/入住人数/备注** → 选择积分抵扣 → 确认费用 → 临时锁房（10 分钟）→ 点击立即支付 → 后端模拟支付成功 → 正式订单自动入后台（待确认）→ 管理员确认（待入住）→ 办理入住（已入住）→ 办理退房（已完成）→ **向下单注册账号发放积分**。

### 5.2 外部订单

第三方平台产生订单 → 管理员从订单管理或房态日历逐笔手动录入→ 校验房态和重复订单 → 按实际状态创建订单 → 办理入住、退房 → **订单已完成且有有效手机号时自动创建/关联会员并按实付金额发积分**。历史已完成订单手动录入成功后立即执行该流程。

### 5.3 取消退款

顾客打开待确认/待入住订单 → 校验北京时间入住当日 18:00 截止 → 申请取消退款 → 后端同步模拟退款并写入成功流水 → 标记已取消、返还已使用积分、释放房间；失败时保持占用与积分不变；异常或失败须可追踪、可重试且不得重复执行。

### 5.4 手动积分发放

管理员进入会员管理 → 按手机号查询、单独创建会员 → 设置初始积分或手动赠送积分 → 确认 → 记录积分流水、变动后余额、原因和时间。

## 6. 核心数据对象与设计约束

| 对象 | 作用 |
|---|---|
| 注册账号 | 直接输入手机号登录；JWT 有效期 30 天；第一期不验证手机号归属、不获取 OpenID |
| 会员 | 等级、累计成长积分、可用积分 |
| 房间 | 基础资料、价格 |
| 封房记录 | 不可订日期区间 |
| 正式订单 | 七种渠道统一订单、状态、注册账号关联、预订人快照 |
| 间夜分摊（查询计算） | 无独立间夜表，按订单区间计算每晚金额及跨月归属 |
| 临时支付交易 | 预支付锁房及超时控制 |
| 支付记录 | 第一阶段模拟支付流水；未来扩展真实微信支付 |
| 退款记录 | 第一阶段同步模拟退款流水；未来扩展真实退款 |
| 入住人/订单入住人 | 实际住宿登记，区别于预订人 |
| 积分流水 | 自动发放、手动发放、抵扣、返还及调整 |
| 积分发放幂等 | 使用积分流水业务唯一号防重复，不强制独立任务表 |
| 订单来源 | 七种固定渠道 |
| 达人 | 所属平台及佣金关联 |
| 经营支出 | 内容、金额、支出日期 |
| 管理员 | 单账号安全登录；不建设通用操作日志表 |

**关键约束：**

1. 预订区间采用 `[入住日, 退房日)`，退房当晚可售。
2. 防止同一房间同一住宿夜晚出现两笔有效订单或有效锁房冲突。
3. 支付回调、退款、积分发放、人工积分发放均需幂等处理。
4. 订单创建后金额不可更改；允许范围内的房间/日期修改须保持晚数并重新计算跨月分摊；积分发放须保存不可覆盖的奖励快照。
5. 注册账号、预订联系人和实际入住人是不同业务实体。
6. 外部订单不生成小程序模拟支付流水；小程序模拟支付必须写入真实的系统业务支付记录，但不代表真实资金收款。
7. 已完成订单不允许取消或进行常规退款；已发放积分不追回。
8. 第一期不接入微信支付；不获取 OpenID，不记录微信手续费，不增加 `pay_type` 字段。
9. 不建设通用审计日志或用户可操作的数据导出/备份功能；支付、退款、积分业务流水必须保存；敏感手机号、住宿登记信息依法保护。

## 7. 第一阶段明确不开发

批量导入订单/会员、用户画像；第三方平台 API 自动同步；顾客自助改期/换房/补差价；多房间合单；多门店；多管理员复杂权限；周末/节假日/动态价格；复杂优惠券、拼团、满减；积分过期；未完成外部订单自动创建会员；已完成订单取消及常规退款；完整财务会计系统；员工排班和库存系统。

## 8. 开发顺序

1. **房间与订单基础**：房间、价格、封房、统一订单、手动录入、状态流转、房态日历。
2. **小程序预订模拟支付**：手机号直接登录、查询、详情、60 天日历、预订表单、10 分钟锁房、模拟支付、自动入后台、模拟退款。
3. **会员积分**：等级、自动发放、手机号手动发放、抵扣、流水、失败重试。
4. **经营管理与报表**：平台达人、支出、今日总览、跨月间夜统计、净营业额和利润。

财务快照、间夜明细、支付退款和积分流水的数据结构必须在前期规划，避免后续返工。

## 9. 验收标准

- [ ] 六间房均可管理、查询、预订，日期冲突被阻止；小程序日历仅显示可预订/不可预订。
- [ ] 小程序模拟支付成功自动生成一笔后台正式订单；未模拟支付成功不生成。
- [ ] 六种外部来源仅由管理员逐笔手动录入，可直接录入已完成的历史订单。
- [ ] 订单状态按待确认→待入住→已入住→已完成流转。
- [ ] 房态日历显示六种正式房态，连住后续夜晚显示「占用」，退房当晚可售。
- [ ] 预订表单仅要求预订人、手机号码、入住人数，备注可选。
- [ ] 退款严格执行待确认/待入住且入住当日 18:00 前的规则。
- [ ] 小程序自动积分归属**下单注册账号**，即使预订手机号不同也不会发错。
- [ ] 管理员可单独创建未登录小程序的会员，支持初始积分与手动赠送。
- [ ] 第三方订单已完成且有手机号时自动建会员并发积分；历史已完成订单手动录入后立即处理。
- [ ] 管理员可通过手机号查询会员并手动发放积分，留存含 `balance_after` 的流水，不增加 `admin_id`/`balance_before`。
- [ ] 同一订单自动积分不重复，失败可重试。
- [ ] 等级门槛为 500/1000/1500，积分抵扣上限 20%；兑换率分别为 30/25/20/15 积分抵扣 ¥1。
- [ ] 手机号直接登录（无验证码、无 OpenID）并签发 30 天 JWT；统一默认头像、手机号后四位昵称且不可修改；可查询房间、查看详情、选择未来 60 天内的入住/退房日期并完成预订。

- [ ] 每日收入按住宿夜晚归属，跨月按间夜数平均分摊实付金额及三类费用，分币尾差后合计一致。

## 10. 待最终确认事项

以下为尚未确定的事项，不能当作已确认规则开发：

1. **外部平台补贴/商家优惠**：顾客实付金额与平台结算金额存在差额时，补贴承担方及差额在经营报表中的归属尚待确认。当前第三方订单录入仅强制填写实付金额。
2. **第三方订单手动录入防重**：有平台订单号时按「平台 + 平台订单号」防重；无平台订单号时管理员自行核对，系统不承诺自动识别全部重复订单。
3. **会员初始积分类型**：管理员单独新增会员后，初始积分通过历史消费补发或赠送/补偿积分流水记录，不直接改写余额。

**已确认且从待确认列表移除**：会员中心底部导航、历史消费/赠送积分与成长积分关系、已完成订单不取消不支持常规退款、微信支付手续费第一期不计入成本或平台手续费、跨月按间夜平均分摊。
