# 芊浔民宿邀请功能第一阶段需求草案

## 1. 目标与范围

在小程序「我的」页面增加邀请入口，让会员分享小程序卡片；被邀请人点击卡片并登录后建立邀请关系。已登录的被邀请人点击卡片后直接尝试绑定，不要求退出或重新登录。邀请人可查看邀请人数和邀请记录。

本阶段只建立和展示邀请关系，不计算、承诺或发放返现，不接入商家转账。第二阶段不补发其上线前订单的奖励；具体奖励规则和生效时点届时另行确认。

本功能为 V3.1 基线之外的扩展，实施前需同步数据库与接口专项设计；本文件不直接改变既有接口契约。

## 2. 已确认业务规则

1. 每位会员具有专属邀请标识，标识不设常规有效期，用于识别邀请人，不包含手机号等个人信息。
2. 新用户和老用户均可被邀请。一位被邀请人只能绑定一位邀请人；绑定成功后，点击其他人的邀请卡片也保留原关系，不自动更换。
3. 不能自己邀请自己；不同会员之间允许相互邀请。
4. 被邀请人通过邀请卡片进入时，若已登录则直接尝试绑定；若未登录，登录成功后尝试绑定。无需立即下单。
5. 绑定失败不向用户提示，用户继续正常使用小程序；不得因此影响登录和正常浏览。系统仍应在服务端记录必要的异常信息，避免记录完整手机号或邀请标识等敏感信息。
6. 同一被邀请人并发触发多个绑定时，先成功写入的关系生效，数据库唯一约束防止重复绑定。重复提交已有关系不得产生重复记录。
7. 邀请人数为该邀请人已成功建立的邀请关系数量；记录展示被邀请人手机号前三位、后四位和绑定时间，不展示完整手机号。
8. 邀请标识长期有效指业务上不设常规过期时间，不保证历史微信卡片不受平台、小程序状态等因素影响。
9. 尚未建立关系时先后点击多张邀请卡片，以最后点击的标识尝试绑定；已建立的关系不更换。
10. 点击卡片后未登录即关闭小程序，之后重新打开并登录，仍尝试绑定上次保留的邀请标识；被更新的卡片标识替换或主动退出登录时清除。

## 3. 业务流程

### 3.1 邀请人分享

1. 会员登录小程序，进入「我的」页面。
2. 点击「联系方式」上方的「邀请好友」，进入邀请页面。
3. 点击分享按钮，由微信展示分享界面，会员主动选择好友或群组。
4. 分享卡片展示民宿信息，并在打开路径中携带邀请人的专属标识；标识不要求展示给好友。

### 3.2 被邀请人进入及绑定

1. 被邀请人点击分享卡片，进入小程序；客户端暂存本次邀请标识，覆盖登录跳转所需过程。
2. 若被邀请人已登录，直接提交绑定请求；若未登录，待登录成功后提交。客户端缓存仅用于传递入口参数，最终关系以后端数据库为准。
3. 后端从可信登录身份获取被邀请人，根据标识查找邀请人，检查标识有效、双方不是同一会员及被邀请人尚未绑定。
4. 校验通过后写入邀请关系。唯一约束处理并发，重复或不符合条件的请求不改变原关系。
5. 绑定未成功时不向用户提示，用户可正常继续使用小程序。绑定成功后也无需依赖后续再次点击卡片来保留关系。

### 3.3 邀请人查询

邀请页面加载当前登录会员作为邀请人的邀请人数及邀请记录。记录仅包含脱敏手机号和绑定时间；空列表显示空状态，请求中及请求失败时提供相应状态和重试方式。查询失败提示与邀请绑定失败静默处理是两个不同场景。

## 4. 页面展示

### 4.1「我的」页面

- 在「联系方式」上方新增「邀请好友」入口，点击进入邀请页面。
- 保持该页面已确认的专用视觉规范及现有页面布局。

### 4.2 邀请页面

- 展示民宿风格的邀请介绍和「邀请好友」分享按钮。
- 展示已邀请人数、邀请记录；每条记录显示如 `138****1234` 的手机号及绑定时间。
- 支持加载中、无记录、查询失败及重试状态；不展示奖励金额、提现余额或返现到账承诺。
- 遵循小程序「江南水乡·雅致古风」视觉基线。分享卡片展示民宿整体形象，不限定某个房间。

## 5. 数据库设计建议

以下为第一阶段设计建议，实施前与数据库 V3.1 专项文档和实际迁移统一确认。沿用 MySQL 8.0、InnoDB、`utf8mb4`，通过新增版本化迁移完成，不修改已应用迁移。

### 5.1 会员表 `members`

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `invite_code` | `VARCHAR(32)` | 会员专属邀请标识，随机生成，不包含手机号；不设常规过期时间。 |

对 `invite_code` 设置唯一索引。既有会员需要回填或在首次使用时安全生成，具体迁移方式实施前确定；并发生成必须依赖数据库唯一约束处理冲突，不应覆盖已分配标识。

### 5.2 邀请关系表 `member_invitation`

| 字段 | 类型建议 | 约束及说明 |
| --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | 主键，自增。 |
| `inviter_member_id` | `BIGINT UNSIGNED` | 邀请人，关联 `members.id`，非空。 |
| `invitee_member_id` | `BIGINT UNSIGNED` | 被邀请人，关联 `members.id`，非空，唯一。 |
| `created_at` | `DATETIME(3)` | 绑定建立时间，非空。 |
| `updated_at` | `DATETIME(3)` | 记录更新时间，非空；创建时初始化。 |

- 对 `invitee_member_id` 建立唯一索引，保证每个被邀请人最多绑定一位邀请人。
- 对 `inviter_member_id` 建立索引，用于统计及查询邀请记录；分页与排序所需组合索引在接口设计时结合实际查询确定。
- 通过服务端校验和数据库检查约束禁止两个会员 ID 相等；允许 A 邀请 B 且 B 邀请 A。
- `created_at` 为绑定时间，`updated_at` 不改变已确认的不可自动换绑规则。时间存储和接口展示遵守项目统一时区约定。
- 邀请人数从关系表统计，不额外存储计数字段。手机号从关联会员读取，并仅返回脱敏结果。

第一阶段无需为建立关系修改 `orders` 表，也不新增奖励或转账表。未来返现需另行确认订单资格、奖励、发放与对账模型；不追溯补发第二阶段上线前订单。

## 6. 权限、可靠性与验收

- 邀请标识不是身份凭证；邀请人和被邀请人的身份以服务端会员记录与登录身份为准，客户端不能指定被邀请人 ID。
- 邀请查询仅能查看当前登录会员自己的邀请统计及脱敏记录。
- 微信分享需用户主动选择接收方；卡片参数可能被转发或修改，后端必须独立校验。
- 手机号直接登录不验证归属，不能作为真实身份或返现防刷的充分依据；第二阶段涉及资金前需重新评估。
- 验收覆盖：新老用户绑定、已登录直接绑定、未登录后绑定、自邀失败、相互邀请、已绑定后点击他人卡片、无效标识、重复及并发绑定、静默失败、登录和正常使用不受影响、邀请人数及手机号脱敏、查询权限边界。

## 7. 实施前待定的技术细节

- 邀请入口参数在冷启动、热启动、登录跳转以及关闭重进时如何传递与清理；需结合微信真机行为和现有导航实现验证。用户未完成登录即离开时不建立关系。
- 已绑定同一邀请人的重复点击应作为幂等操作；对用户无提示。遇到数据库或网络异常时如何安全记录与恢复，需在接口设计中明确，不能静默报告绑定成功。
- 邀请记录的分页大小、排序和具体接口字段由后续接口专项设计确定；不得擅自将其视为现有 V3.1 接口。
- 既有手机号若不符合常见 11 位格式，展示脱敏方式由实施阶段结合现有数据和校验规则确定，任何情况下不得返回完整号码。
