# 邀请功能第一阶段：接口与技术实施方案

> 状态：用户已确认实施。需求依据：[第一阶段需求草案](../01-需求/芊浔民宿_邀请功能第一阶段需求草案_20261121.md)。

## 1. 范围与已确认规则

「我的」页联系方式上方增加入口，会员进入邀请页查询人数、脱敏记录并分享小程序卡片。新老会员点击卡片后，已登录直接尝试绑定，未登录则登录成功后尝试。每位被邀请人最多绑定一位邀请人，不能自己邀请自己，允许双方相互邀请；已有关系不可自动更换。绑定失败不提示且不能阻断正常登录或浏览。邀请标识不设常规有效期。

本阶段不实现奖励、提现、商家转账，也不对第二阶段上线前订单补发奖励。页面不承诺奖励金额及发放时间。

## 2. 仓库现状

- `frontend/miniprogram/pages/my/index.wxml` 已有联系我们卡片；`index.ts` 的 `onShow` 检查会话，适合在此前添加邀请入口。
- `frontend/miniprogram/pages/login/index.ts` 登录成功后调用 `saveSession` 并 `switchTab` 首页；`onShow` 发现有效 token 也会跳首页。邀请流程必须覆盖这两条路径。
- `frontend/miniprogram/app.ts` 目前只有会话全局状态；`app.json` 的首页是 tabBar 页面，分享落地应使用新建的非 tabBar 页面，避免跳 tab 丢失参数。
- `frontend/miniprogram/services/request.ts` 收到 401 会清会话并强制跳登录。静默绑定请求需专门适配，以免网络、授权失败影响用户当前页面。
- `backend/.../modules/auth/controller/AppAuthController.java` 已有 `POST /api/app/auth/login`，会员身份来自 JWT `AuthPrincipal`；`modules/member/mapper/MemberMapper.java` 与 `mapper/member/MemberMapper.xml` 负责会员 SQL。
- `backend/src/main/resources/db/migration/V1__create_members_and_admin.sql` 已有 `members`，迁移现有最高版本为 V14；`orders.member_id` 已存在，但本期不使用订单表。
- 现有 API 使用 `ApiResponse`、snake_case、会员 JWT 与 `list/total/page/size` 分页；时间转换可参考 `common/util/ApiTime.java`。具体文件路径见第 7 节。

## 3. 方案与数据流

### 3.1 邀请标识

首次进入邀请页时，通过带认证的 POST 初始化或获取当前会员的持久邀请标识。建议使用 `SecureRandom` 生成 128 位随机值，编码为 22 位无填充 URL-safe Base64；不含手机号或会员 ID。相同会员后续获取固定标识。数据库唯一索引与条件更新处理并发和碰撞；不能以 GET 产生写入副作用。

`members.invite_code` 允许为空，老会员和新会员均按需初始化；避免一次性回填及修改所有会员创建入口。唯一索引允许多个 NULL；邀请码采用二进制区分大小写的字符集排序规则。首次分享前接口失败时不可发送不含标识的邀请卡片，应显示邀请页面加载失败及重试；这属于邀请人获取分享信息失败，不是被邀请人的绑定失败提示。

### 3.2 分享、接收、绑定

1. 邀请页从服务端获得标识；通过 `button open-type="share"` 和页面 `onShareAppMessage` 配置标题、图片及路径 `/pages/invitation-entry/index?code=...`。该入口不放房间信息，不从客户端生成邀请标识。
2. 新建落地页读取并校验参数格式，保存单个待处理标识到独立的本地存储项；不存手机号或 token。在相同入口重复触发时幂等处理。分享卡片被第三人转发仍归属原标识对应邀请人。
3. 有有效会话则静默提交；无会话则引导现有登录页，登录成功保存 JWT 后静默提交，再正常进入首页。此前已登录的 `onShow` 自动跳转路径也应触发待处理消费。落地页和登录页的过渡不得阻塞正常浏览。
4. 服务端只从 `AuthPrincipal` 获取被邀请人；通过标识查邀请人，检查非本人后插入。事务与唯一约束保证已绑定关系不变；发生唯一冲突时按幂等方式处理，不能覆盖或更新已有关系。
5. 客户端在服务器确认请求已处理（含已经绑定、无效标识、自邀）后清除本地待处理标识；网络故障或 5xx 时保留，下一次应用进入或登录后静默重试，不循环重试、不阻断用户。用户主动退出登录时清除待处理标识，避免跨账号误绑定。应用关闭重启可恢复待处理信息；只有登录成功才发绑定请求。
6. 同设备收到新邀请入口时，以最近一次点击的标识替换尚未提交或处理失败的标识；服务端已有绑定仍永不更改。

**并发注意：**本地状态须带请求时的标识版本；旧请求完成时只清除仍与该请求匹配的标识，防止误删新点击的卡片信息。异步绑定任务持有发起时的 token，会话变更后不应拿新账号重试旧标识。

### 3.3 查询与隐私

以当前 JWT 会员作为邀请人查询，不接受客户端提供邀请人 ID；仅返回手机号前三位、后四位和绑定时间，不返回完整手机号、会员 ID 或邀请人隐私。对不符合 11 位数字格式的存量手机号，统一返回 `****`，避免意外泄露。按 `created_at DESC, id DESC` 稳定排序，使用 `total` 作为已邀请人数。

## 4. 接口设计建议（新增，待确认）

统一使用 `Authorization: Bearer <token>`，响应 `{"code":200,"message":"success","data":...}`；HTTP 错误遵循项目现有规范。以下路径均为建议，不是既有 V3.1 接口。

### 4.1 获取或初始化邀请标识

`POST /api/app/invitations/share-code`，无请求体。用于受认证会员首次生成并读取固定标识，后续返回同一值。

```json
{"code":200,"message":"success","data":{"invite_code":"AbCdEf0123456789_-XYZA"}}
```

匿名请求 401；服务异常 500。分享页面仅在获取成功后允许分享；无须申请好友列表或支付权限。

### 4.2 尝试绑定邀请关系

`POST /api/app/invitations/bind`：

```json
{"invite_code":"AbCdEf0123456789_-XYZA"}
```

合法格式且已认证时，统一返回 `{"code":200,"message":"success","data":{}}`，无论是新建、已绑定、自邀还是标识不存在；不披露邀请人或已有关系。格式非法 400，未认证 401，服务异常 500。客户端对所有绑定失败静默处理；400 为终止并清除，401 清除或等待有效登录须与当前会话状态对应，网络和 5xx 保留后重试。不能把异常返回伪装成成功；成功仅表示该请求已处理，不声称一定创建关系。

不修改登录接口：分享来源只通过独立绑定请求传递，避免影响已有调用方及登录事务。调用方不能传入被邀请人 ID。

### 4.3 查询邀请记录

`GET /api/app/invitations?page=1&size=20`，参数 `page` 从 1 开始，`size` 默认 20；建议最大 100，越界返回 400。

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "list": [{"masked_phone":"138****1234","bound_at":"2026-11-21T14:30:00+08:00"}],
    "total": 1,
    "page": 1,
    "size": 20
  }
}
```

`total` 即邀请人数；无记录时 `list` 为 `[]`、`total` 为 0。排序为绑定时间、关系 ID 倒序，明确时间为 Asia/Shanghai 的 ISO 8601。拒绝未认证请求；仅查当前会员自己的记录。

## 5. 数据库与迁移设计

新增 `V15__create_member_invitations.sql`，版本在实施前重新核对避免冲突。禁止修改已应用迁移或执行清库。

### `members`：新增字段

`invite_code VARCHAR(32) CHARACTER SET ascii COLLATE ascii_bin NULL`，唯一索引 `uk_members_invite_code`。采用按需生成，不回填、不设置默认值；其他现有会员字段与表行为不变。唯一碰撞时重新生成；同一会员并发首次申请采用条件更新 `WHERE invite_code IS NULL`，失败后读取既有值。若持久化异常向调用方返回 500，不能生成不持久的卡片。

### `member_invitation`：新增表

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | 主键自增 |
| `inviter_member_id` | `BIGINT UNSIGNED` | 非空，外键 `members(id)` |
| `invitee_member_id` | `BIGINT UNSIGNED` | 非空，外键 `members(id)`，唯一索引 |
| `created_at` | `DATETIME(3)` | 非空，创建时间 |
| `updated_at` | `DATETIME(3)` | 非空，创建及更新时维护 |

添加 `CHECK (inviter_member_id <> invitee_member_id)` 及查询索引 `(inviter_member_id, created_at, id)`。日期采用数据库与应用既有统一时区约定，输出显式 +08:00；先核对现有部署实际时区及 `ApiTime` 行为，不依赖服务器默认时区。绑定关系本期不提供删除或换绑接口。

部署顺序为先迁移再发布兼容代码；代码回滚时保留新增字段及数据，避免丢失已建立关系。若需撤销结构须另行审批；不执行破坏性回滚。

## 6. 安全与可靠性

- 邀请码为可被分享的公开标识，不应视为授权凭证；卡片链接和日志不含手机号及完整 token，日志对邀请标识做脱敏或不记录。
- 基于现有手机号直接登录无法证明真实身份，可建立邀请关系但不能作为未来现金发放的充分身份或防刷依据。
- 静默不等于吞掉故障：记录不含敏感内容的错误类型与监控；调用失败不影响登录/首页。普通邀请列表查询失败可显示重试。
- 分离绑定请求对 401 的处理：采用独立的静默请求，不触发 `request.ts` 全局强制跳转；其他请求保留原行为。token 过期或 401 不得导致以另一个账号误绑定。
- 限制请求和标识长度；异常与参数按统一异常处理，防止遍历和信息泄露。平台分享 API、冷/热启动及页面栈行为需使用微信开发者工具及真机实测，不能仅靠模拟器断言。

## 8. 实施顺序及验收

1. **契约与迁移**：确认第 4、5 节并同步数据库及接口专项文档，新增 V15。验收：空库和现有库均可迁移；存量会员不变；数据库拒绝自邀和重复被邀请人。
2. **后端服务与接口**：实现标识初始化、绑定及分页查询，加入授权、校验和统一异常。验收：重复获取标识稳定；新老会员可绑定；自邀无记录；已绑定不能换绑；不同会员可相互邀请；只返回本人的脱敏记录。
3. **前端流程**：新增入口及分享落地，处理登录前后和静默失败。验收：已登录和未登录用户均可建立关系；无网络、无效码及已有关系不妨碍浏览；分享卡片携带持久标识；记录页人数与记录正确。
4. **并发与恢复**：验收真实 MySQL 下同一被邀请人并发绑定至多一条；同会员并发生成标识最终只有一个持久值；重试不改写关系；旧请求不清除新标识；退出及换账号不串绑。
5. **发布验证**：迁移与后端先于小程序上线，微信开发者工具及真机验证从聊天卡片的冷/热启动、登录跳转、重复进入、过期会话与分享转发。回滚应用时保留关系数据。

## 10. 待确认与实现前核实

- 已确认：尚未建立关系时先后点击多张卡片，最近一次点击的标识取代未处理标识；先成功绑定后永不自动更换。
- 已确认：未登录时点击卡片后关闭小程序，之后再次打开并登录仍尝试绑定；标识保留至成功处理、主动退出或被更新的邀请入口替代。
- 设计基于长期有效邀请标识及当前手机号登录；无持久停用/封禁机制的需求，不在本期引入。
