# 邀请首单奖励实现方案

> 状态：待用户审阅；本文件为方案，不代表接口、数据库变更已实施。日期：2026-11-25。

## 已确认需求

- 每个被邀请人仅对第一笔符合条件、完成的房间订单产生一次邀请奖励，金额为实付金额的 10%；商城订单不参与，取消、退款的订单不占用机会。
- 房间订单须在功能生效时点之后且邀请关系绑定之后支付成功，并在之后完成退房。上线前已支付或绑定前已支付的订单不参与，也不回填历史订单。
- 邀请人小程序邀请记录显示红色“未下单”或绿色“已下单”，仅在符合条件的订单完成后转绿；不展示奖励金额。后台仅管理员查看邀请人、被邀请人、订单、实付和奖励金额。只计算记录，不自动发放。
- 增加奖励是否已发放的记录，供管理员辨别；发放仍由人工在系统外进行。管理员手动标记，已发放不能改回未发放。
- 奖励保留两位小数，第三位四舍五入；零实付订单产生 0.00 元并占用一次机会。

## 现状与方案选择

现有 `member_invitation` 唯一约束每个被邀请人，记录双方和绑定时间；`orders.member_id` 标识小程序下单会员，`order_amount.paid_amount` 是不可编辑的金额快照，`payments` 保存支付成功状态和时间。`OrderCommandServiceImpl.performAction` 已在退房事务中改状态并奖励积分；`GET /api/app/invitations` 当前仅返回脱敏手机号与绑定时间。后台无邀请页面。

**不需要新建表。**每个邀请关系最多一个奖励，与既有关系一对一，直接在 `member_invitation` 增加获奖订单 ID、奖励金额和发放标记即可；查询时关联既有订单和金额表。独立奖励表也可实现，但当前没有多次奖励或发放流水需求，额外表不必要。只改查询而不持久化获奖订单无法稳定锁定首个完成的订单及历史金额。

## 数据库与生效边界

- `member_invitation` 修改：新增 `reward_order_id BIGINT UNSIGNED NULL`，外键指向 `orders.id`，加唯一索引；新增 `reward_amount DECIMAL(12,2) NULL`，非负，二者同时为空或同时非空。空代表未产生奖励；金额为零也是已产生奖励。按现有 Flyway 最大版本加一创建迁移，禁止修改既有迁移；现有行保持 NULL，不回填。
- 同表新增 `reward_issued BOOLEAN NOT NULL DEFAULT FALSE`：仅表示人工记录的发放标记，不代表系统已转账；仅有获奖订单的关系可标为已发放。无奖励显示“无奖励”，不能仅依据 false 显示“未发放”；有奖励时依标记显示“未发放”或“已发放”。现有数据默认 false。管理员可手动标记已发放，不可撤销。
- `orders`、`order_amount`、`payments`、`members` 均不改结构：分别提供下单会员与订单号、实付快照、成功支付及支付时间、会员信息。`order_amount` 生成列不写入。
- 按用户后续确认，V20 迁移完成后的下一整秒自动生效；生效边界使用数据库 Flyway 迁移历史，换算为北京时间。无需人工配置，重启和多实例使用相同边界；旧服务与新服务不可混跑。支付时间必须不早于该边界，且严格晚于邀请绑定时间。
- 支付记录以 `order_id` 与成功状态关联，按小程序下单会员 `orders.member_id` 识别，不用预订联系人手机号识别。核实项目支付渠道及支付成功字段，兼容仓库已有模拟/微信支付方式；不引入或改动支付流程。
- 以完成动作的数据库串行化顺序决定首笔完成：订单完成事务在修改状态前先锁定下单会员，再锁住邀请关系行，若尚未关联奖励且订单满足条件，写入订单 ID 和按实付金额算出的奖励；已有奖励则跳过。退房状态、积分和邀请奖励同事务提交，失败则回滚。不同房间同一被邀请人同时退房时，关系行锁和条件更新保证只记录一次；重复操作幂等。落实与现有房间、订单、会员锁顺序的兼容并用真实 MySQL 测试死锁/回滚。订单直接导入为已完成的第三方渠道不属于小程序会员支付记录，不能通过手机号匹配。

## 接口影响（方案，实施前须确认契约）

| 方法和路径 | 变更 | 用途与兼容 |
| --- | --- | --- |
| `GET /api/app/invitations` | 修改 | 每项新增 `has_completed_order` 布尔字段；依据奖励订单是否存在返回，原字段、分页和仅本人权限不变；不返回奖励金额或订单。旧客户端忽略新增字段。 |
| `GET /api/admin/invitations` | 新增 | 管理员分页查看所有邀请关系及其奖励；每项返回邀请人、被邀请人必要身份信息、绑定时间、是否已完成合格订单、订单号、实付、奖励金额和发放标记；无订单时相关订单金额字段为 null，发放标记不得单独解释成有未发放奖励。手机号仅用于后台辨认，展示策略沿用现有后台会员权限与隐私约定。按绑定时间和关系 ID 倒序。金额为十进制字符串。 |
| `PUT /api/admin/invitations/{id}/reward-issued` | 新增 | 管理员以 `reward_issued: true` 标记已发放，不触发真实转账。 |
| `POST /api/app/invitations/share-code`、`POST /api/app/invitations/bind` | 不变 | 继续沿用已有分享和绑定规则。 |

新增接口及字段属于现有契约扩展，先审阅批准，并同步需求、数据库及接口专项文档；后台接口采用现有管理员 JWT 安全规则，普通会员无权访问。零元奖励不能以金额是否大于零判定状态。

## 页面与流程

1. 管理员办理退房：沿用原订单动作，完成与邀请奖励写入同事务；失败不宣称成功。
2. 小程序邀请页：复用现有列表和分页，仅添加红色“未下单”、绿色“已下单”文字标签；保留图片、分享与布局主结构，遵循 `DESIGN.md`，非仅靠颜色表达。红色的业务含义是“尚无符合规则的已完成订单”，不代表从未支付。
3. 后台增加“邀请记录”入口与分页列表，显示双方身份、绑定时间、完成状态、订单号、实付、应得奖励及发放状态；无符合条件订单显示“无奖励”。管理员可手动标记已发放；不设计自动发放、导出或转账功能。

## 实施步骤与验收

1. **契约和迁移**：确认方案后补充三份扩展文档、建立迁移并自动固定生效时间。验收：旧数据无奖励、原邀请关系不变；约束拒绝一单关联多份奖励和不完整金额记录；空库和现有库迁移成功。
2. **奖励业务**：邀请 Service 提供退房时幂等计算；订单事务调用，Mapper/XML 完成行锁、条件更新及支付校验。验收：只有上线并绑定后支付且已完成的房间单可产生日志记录；取消或退款后再下单可奖励，重复退房不重复计算；完成与奖励原子提交。
3. **查询接口**：扩展小程序邀请列表；新增管理员分页接口并复用统一鉴权/响应。发放标记写入接口要求管理员权限。验收：用户只看到本人关系及布尔状态、不能读取奖励；管理员看到双方和订单、实付、奖励及发放状态；无记录时空列表，分页稳定。
4. **页面**：实现管理后台入口和列表、小程序状态标签。验收：后台数据列与表头对齐、加载/空/失败可见；小程序未完成红色、完成绿色，文字可辨；原分享与分页正常。
5. **质量检查**：后端编译与相关测试、后台构建、小程序类型检查和相关测试；实际微信开发者工具可用时检查视觉，未使用时明确说明。

## 验证重点与风险

- 测试金额两位舍入、积分抵扣后实付、零元、无关系、非本人订单、绑定前/上线前支付、生效临界时刻、支付未成功、取消退款、商城订单、第二次完成订单、发放标记与无奖励区分、请求重试、后台和小程序权限隔离。覆盖发放标记操作及并发测试。
- 真正的 MySQL 8 集成测试覆盖两笔不同房间订单并发退房、关系行锁、唯一约束、失败回滚；不能以 H2/mock 宣称并发正确。模拟和真实微信支付均沿用既有模式并覆盖成功流水匹配。
- `paid_at` 的来源、数据库时间精度和历史记录一致性在实现前验证。支付与绑定在同一毫秒时按严格大于排除，存在极小边界误判；若业务要求精确仲裁，需改用共享锁或可靠事件顺序并重新确认。
- 当前手机号直接登录不验证归属，奖励涉及后续人工发放时，管理员需自行核对身份；此方案不新增身份核验、反作弊或自动支付。
- 部署前备份；迁移可向前兼容旧版本，但新旧服务混跑会漏记完成动作，发布应避免混跑并检查上线后漏记。回滚应用前保留字段和数据，不执行破坏性回滚；后续重新启用如何补记需另行确认。
