# 芊浔民宿线上商城实现方案

> 日期：2026-11-22；状态：待审阅。本文为实现建议，接口路径、字段与迁移须在开发前作为 V3.1 扩展契约确认；不代表已经实现或验证。

## 1. 目标与已确认范围

新增独立商品商城：一单一种商品、可购买多件；商品上下架、不管理库存，规格写在描述里，不计运费。支付成功后才创建正式订单，状态为待发货、已发货、已完成或已退款；一单一个包裹，管理员录入快递信息、完成订单。仅待发货支持整单退款，已发货联系商家。商品名称和收货信息保存订单快照，不保存商品封面或描述快照；付款成功才更新默认收货信息。待支付期间改价或下架不改变该次支付价格。

积分和支付沿用现有房间预订规则：会员共用积分、按等级兑换且抵扣不超过商品总额 20%，预支付时预占、成功时扣减，退款成功返还抵扣积分，订单完成时按实付金额向下取整奖励可用积分与成长积分，每单一次。仅记录既有邀请关系，无返现；商城不进入住宿经营报表。用户指定暂不展开退款与发货同时发生的业务规则，本方案将此作为上线前风险，不擅自确定冲突胜负。

## 2. 现状与约束

- `backend/src/main/resources/db/migration/V4__create_availability_tables.sql`：住宿 `orders` 强制房间、渠道和日期；不适合商城。V7 的 `payments.booking_id` 指向 `booking_lock` 且非空；V8 的 `refunds` 指向住宿订单和支付。分别新增商城表，保留历史数据。
- `backend/src/main/java/com/qianxun/homestay/modules/points/service/impl/PointsBalanceServiceImpl.java` 当前只通过 `BookingLockMapper.sumReservedPoints` 计算住宿预占；抵扣及返还流水的 `ref_no` 以住宿订单 ID 构造，不能直接用于商城。
- `backend/src/main/java/com/qianxun/homestay/modules/payment/service/impl/WechatPaymentServiceImpl.java` 微信通知已验签但后续绑定住宿结算；`WechatPayNotificationController.java` 提供原有两个回调。需按可验证的全局唯一商户单号分流，维持原回调地址和签名校验。
- `backend/src/main/resources/db/migration/V6__create_points_log.sql` 的 `order_id` 外键指向住宿订单；商城须增加独立关联，并保留现有流水和唯一引用号。
- `frontend/miniprogram/app.json` 已有首页、订单、会员、我的四个底部入口；`frontend/admin/src/router/index.ts` 使用现有后台路由。小程序采用项目确认的江南水乡视觉令牌。
- `README.md` 说明部署默认模拟支付，启用微信配置后新交易走微信；用户要求商城与项目当前开启模式一致，不假设每个环境均开启真实微信支付。微信生产配置是否已开启未核实。
- 用户的 `docs/01-需求/芊浔民宿_线上商城需求文档.md` 是未跟踪文件，保留原样。此前聊天需求草案尚未另行保存成经确认文件。

## 3. 总体设计与数据流

新增 `modules/mall` 负责商品、商城订单、商城支付快照和退款；Controller → Service 接口 → ServiceImpl → Mapper/XML，DTO/Entity/VO 分离，业务类及关键逻辑使用中文注释。支付网关、会员身份、积分余额、统一响应与异常复用现有能力；住宿和商城的业务结算分别处理。Service 间通过接口协作，避免循环依赖。金额 `BigDecimal`，JSON 金额字符串；业务时间采用 Asia/Shanghai，时间输出含时区。

```text
小程序 -> 商品/下单 -> 锁会员并计算两种业务的积分预占 -> mall_payment 保存快照
       -> 当前启用的支付渠道 -> 回调验签/查单 -> 商城结算事务
       -> mall_order + 扣积分流水 + 默认地址 + mall_payment 成功
管理员 -> 发货/完成 -> 订单状态；完成事务内奖励一次积分
用户 -> 待发货退款 -> mall_refund -> 支付渠道结果确认 -> 退款/订单/返积分事务
```

支付重复请求和通知使用稳定唯一号及数据库约束防重；支付关闭前核实渠道结果，未知时保留积分预占并对账。跨商城、住宿统一会员行锁和锁顺序，防止并发多占积分；明确将两边 PENDING 且仍应保留的预占计入余额，不能仅按超时时间忽略微信结果不明的交易。商城支付成功关联的订单唯一，金额、商户、付款人、交易号与渠道结果核验。事务不包裹远程微信请求；通知延迟、失败、重试与关单结果不确定需可恢复并留可排障日志，日志不输出地址、手机号或密钥。

## 4. 数据库变更清单（拟新增 Flyway V16，实施前确认最新版本）

已有迁移不修改；新表 InnoDB、utf8mb4、金额 DECIMAL(12,2)、ID BIGINT UNSIGNED、DATETIME(3)。这些为拟议字段，名称与长度在扩展契约确认后确定。

| 表 | 拟新增字段 | 用途与约束 |
| --- | --- | --- |
| `mall_product` 新增 | `id,name,description,images,price,status,created_at,updated_at` | 商品维护；图片 JSON；价格非负，上架状态索引；不新增库存、规格表 |
| `mall_order` 新增 | `id,order_no,member_id,product_id,product_name,quantity,total_amount,paid_amount,points_used,recipient_name,recipient_phone,shipping_address,status,express_company,tracking_no,paid_at,shipped_at,completed_at,created_at,updated_at` | 一单一商品快照；订单号唯一、会员与状态索引；快递及时间可空，金额与数量检查 |
| `mall_payment` 新增 | `id,payment_no,mall_order_id,member_id,product_id,product_name,quantity,total_amount,points_used,amount,recipient_name,recipient_phone,shipping_address,payment_method,transaction_id,wechat_prepay_id,status,expires_at,paid_at,created_at,updated_at` | 同一行持久化待支付快照与支付流水；支付号、交易号及关联订单唯一，会员/状态/过期索引；`mall_order_id` 支付前为空 |
| `mall_refund` 新增 | `id,mall_order_id,mall_payment_id,refund_no,wechat_refund_id,amount,status,refunded_at,created_at,updated_at` | 独立退款跟踪，商户退款号、渠道退款号唯一；按订单查询退款。成功与处理中请求防重，明确失败后可安全重试 |
| `members` 修改 | `default_recipient_name,default_recipient_phone,default_shipping_address` | 均可空；支付成功后更新；旧会员不回填 |
| `points_log` 修改 | `mall_order_id` | 可空外键/索引，原 `order_id` 不变；新引用号使用商城专属命名空间，防止两类 ID 重号；旧流水不回填 |

不新增商品订单明细表、单独待支付表、多地址表或邀请表；订单商品信息和待支付信息分别放订单、支付表。原 `orders/payments/refunds` 保持结构和业务含义。迁移仅新增结构；回滚前须停止新商城流量并核对、保全商城交易及积分数据，不能直接删除已有数据。

## 5. 接口清单（新增路径均为建议，须先确认扩展契约）

现有住宿接口及微信回调 URL 保持兼容；现有房间预占与积分预览内部计算需同时计入商城预占。商城接口使用统一响应、snake_case、分页规则，会员 JWT 只能访问本人交易，管理员 API 使用管理员角色；公开浏览是否开放匿名遵循现有安全策略，当前先按会员访问设计。

## 7. 分步实施与验收

1. **确认扩展契约和迁移**：编写三份商城扩展文档与 V16；验收：四表、两处现有表扩展均可由 MySQL 8/Flyway 应用，旧会员与订单无需回填。依赖：审阅方案与接口/数据库字段确认。
2. **商品与会员地址**：新增商品管理、列表和默认地址读取；验收：管理员可维护上下架，用户不能下单购买未上架商品，未支付不更新地址。
3. **支付快照及共同积分预占**：实现服务端报价、会员行锁、两类预占合计及待支付过期处理；验收：并发房间与商城请求不能预占超过余额，改价/下架不改变有效快照，支付结果未知不提前释放。
4. **支付结算与回调**：接入当前开启的模拟或微信模式，按验签结果分流；验收：成功只生成一个待发货订单、扣一次积分、保存地址；通知重放、金额或身份不符不重复结算。
5. **订单、发货、完成与退款**：实现本人订单查询、管理员发货与完成、整单退款及奖励/返还；验收：状态与角色校验生效，重复完成/退款不重复发积分；已发货自助退款拒绝并提示联系商家。
6. **小程序和后台页面**：接入已确认接口；验收：商品浏览、购买、订单、管理和快递操作可完成，异步加载、空态、失败和重复提交有明确反馈，界面遵循现有设计规范。
7. **联调与回归**：执行下节验证并记录结果；验收：对应测试通过或对环境限制和未覆盖项如实记录。

## 8. 验证策略

| 范围 | 验证内容 |
| --- | --- |
| 业务与权限 | 正常、无效数量或地址、下架、会员越权、管理员权限、非法状态、重复请求、订单快照 |
| 积分 | 不同等级/20% 边界、共同预占、房间与商城并发、支付扣减、退款返还、完成奖励及重复防重 |
| 支付与退款 | 模拟与微信模式选择、验签、金额及付款人校验、回调重放、关闭/支付竞争、未知结果对账、退款处理中/成功/失败及重试 |
| 数据与并发 | MySQL 8 实测事务回滚、唯一键、行锁及竞态；不用 H2 或 mock 替代并发正确性证明 |
| 兼容性 | 现有住宿预订、支付、退款、积分、报表结果回归；商城收入不进入原报表 |
| 前端 | 类型检查、后台构建、微信开发者工具关键流程及安全区；长地址和错误状态 |

计划执行：`mvn -s backend/maven-settings/aliyun.xml -f backend/pom.xml test`、`npm --prefix frontend/admin run build`、`npm --prefix frontend/miniprogram run typecheck`；MySQL Testcontainers 需要 Docker。真实微信支付和退款须具备商户配置与可公网访问回调后独立联调，不以本地模拟通过代替。本文为计划，尚未执行这些测试。

## 9. 风险与未决事项

- 用户要求暂不考虑退款和发货同时发生；真实异步退款可能产生该情形。当前不定义产品处理方式，也不能宣称相关安全性已验证；正式上线前需要单独确认处理规则并补充测试。
- 微信支付与本地事务无法构成单一数据库事务：必须有可重试对账及幂等恢复，不能将未确认渠道结果当作关闭或成功。
- 会员默认地址保存姓名和收货手机号属于对先前草案的实现解释；如果仅允许在会员表保存地址，需调整默认值展示行为。
- 商品图片已有地址的来源和上传能力尚未核实；不假设可直接使用不存在的上传接口。
- 会员手机号直接登录的既有身份风险、收货信息访问控制及脱敏日志需保持可见；不能声称已验证手机号本人身份。
- 此方案仅提出新增 API/表和迁移，不能绕开 AGENTS.md 对确认契约和数据库变更的要求；未批准前不实施。
