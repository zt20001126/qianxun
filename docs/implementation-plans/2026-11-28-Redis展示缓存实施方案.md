## 1. 目标与范围

Redis 仅作为可丢弃的展示数据副本，MySQL 保持业务事实来源，COS 保持图片文件来源。先缓存小程序房间基础资料、商城上架商品详情和分页列表；后台查询继续直查数据库。接口、权限、金额计算、订单和支付流程保持现有契约。

图片二进制不进入 Redis。不引入 Redis 库存扣减、Redis 锁房、Redis 积分账本、消息队列或第二级本地数据缓存。图片下载提速由缩略图、压缩和 COS/CDN/HTTP 缓存另行处理。

本次需求和代码信息足够形成建议方案，无需再确认是否允许引入 Redis。展示数据的可接受延迟仍是审阅项：建议接受下述短暂旧数据窗口；若要求管理员下架完成后所有新查询立即看不到商品，需调整为实时数据库状态校验，不能直接承诺本方案提供强一致性。

## 3. Redis 中具体存什么

所有业务数据采用 String key + 明确类型的 JSON value；金额保留十进制精度，不使用 double。缓存模型独立于 Entity，不把数据库对象直接作为接口响应。环境前缀和结构版本必须进入 key。

下表以 qx:prod:v1 为示意，环境名来自配置。

| 缓存 | key 示例 | value | 建议 TTL |
|---|---|---|---|
| 房间基础目录 | qx:prod:v1:{rooms}:<代次>:catalog | 已启用客房的基础快照数组：id、房号、名称、楼层、展示价格、人数、床型、面积、设施、原始 images、描述 | 120 秒，加 0～15 秒随机量 |
| 商城商品详情 | qx:prod:v1:{mall}:<代次>:product:12 | 上架商品展示快照：id、名称、介绍、images、展示价格、状态、时间字段 | 120 秒，加 0～15 秒随机量 |
| 商城分页 | qx:prod:v1:{mall}:<代次>:page:1:20 | 同次加载得到的 list/total/page/size；默认仅缓存 size=20 的前 5 页，范围由配置控制，其余直查 | 30 秒，加 0～5 秒随机量 |
| 房间图片签名 | qx:prod:v1:image-sign:<摘要> | 签名 URL、签发时刻、绝对失效时刻；摘要包含桶、地域、对象 key、签名配置代次，不包含密钥 | 最长约 50 分钟，且必须早于签名到期至少 5 分钟 |
| 缓存代次元数据 | qx:prod:v1:{rooms}:generation / qx:prod:v1:{mall}:generation | 随机 UUID；每次相关维护事务成功后换一个新值 | 不设 TTL；只有两个小 key，丢失后生成全新 UUID |

先缓存六间房目录，不再同时缓存房间列表、每间详情、每个日期组合的整套响应，避免同一份资料存在多个副本。详情按 id 在目录里查找。不得缓存 available 字段；传日期时仍每次调用原 AvailabilityService 过滤整个住宿区间。

签名缓存是独立于房间资料缓存的复用层：房间目录存原始引用，返回 VO 时再解析。只有需要签名的旧引用进入签名缓存；普通公开链接不需要单独再存一份 URL 映射。配置轮换或部署改变 COS 映射时提升签名配置代次，旧签名 key 自动到期。任何日志不得输出完整签名链接。

暂不缓存：可订状态、封房、有效锁房、会员身份与地址、积分余额与预占、订单/支付/退款状态、报表、经营支出、渠道字典、JWT、图片二进制。没有读取性能证据时不扩大范围。

## 4. 一致性设计

### 4.1 读取和回填

1. Service 完成参数和权限校验，再进入展示缓存服务。后台和交易查询绕过缓存。
2. 取得当前领域代次；不存在时 SET NX 创建随机 UUID，竞争失败后重读，禁止用固定 0 作为默认代次。
3. 使用代次组成数据 key。命中且未超过 value 中的绝对 freshUntil 时返回；不因命中续期。
4. 未命中，从 MySQL 主库加载。记录数据库读取开始时刻，缓存截止时间从该时刻计算，避免慢查询结束后才重新开始整段 TTL。
5. 用 Lua 原子检查当前代次仍等于读取时的代次，且截止时间未过，才写缓存并设置剩余 TTL。代次改变则丢弃回填；可重试一次最新代次查询，持续变化时直查返回且不回填。
6. Redis 超时、反序列化失败、代次异常或脚本失败时回退数据库，不返回自造空列表、不伪装成业务 404。缓存逻辑不得吞掉数据库和业务异常。

Lua 的代次 key 和数据 key 使用相同 {rooms}/{mall} hash tag，保证未来使用 Cluster 时位于同一 slot。当前部署仍采用单实例，不新增集群。

### 4.2 写入后失效

保留现有数据库事务。createRoom/updateRoom/setRoomEnabled 成功提交后旋转 rooms 代次；商城 create/update/setStatus 成功提交后旋转 mall 代次。一个商城代次同时覆盖详情、列表、总数，无需遍历分页 key。

通过 TransactionSynchronizationManager 的 afterCommit 注册失效动作：事务回滚时不切换代次；无事务时明确立即执行。禁止只依赖 @CacheEvict 默认方法结束时机，也禁止在事务提交前删除缓存后让并发请求回填旧数据库值。

代次切换成功后，新请求只读取新代次 key。旧代次数据不再可达，等待短 TTL 自动释放；不用 KEYS、FLUSHDB 或全库清理。写操作不直接把传入 DTO 写成缓存，防止漏字段及旧更新覆盖新更新。

这解决常见竞态：读请求先查到旧库值，写请求提交并失效，读请求最后又回填旧值。回填的 Lua 代次检查会拒绝它。已在执行、已取得旧缓存的请求仍可能返回旧资料，不能把它描述为线性一致性。

### 4.3 失效失败和进程崩溃

MySQL 和 Redis 没有原子联合提交。数据库已提交而 Redis 旋转失败，或应用恰好崩溃时，旧数据可能保留到过期；afterCommit、代次或延迟双删都不能消除这个事实。

建议初期允许展示资料最终一致：详情最长约 135 秒、列表最长约 35 秒的缓存陈旧窗口；数据库加载超时也必须受控，禁止旧快照重新获得完整 TTL。签名本身在图片内容引用未变时可复用更久，不决定房间图片数组更新窗口。

afterCommit 失效失败：保留数据库成功结果，记录领域、操作和失败指标；本进程暂时绕过该领域缓存，并以有界退避任务重试旋转。重试任务不是持久化保证，进程崩溃/其他实例仍依赖 TTL。不能因 afterCommit Redis 异常把已落库操作表现成数据库回滚。

Redis 重连恢复时先旋转两个领域代次再恢复本实例缓存读取；缓存 value 保留绝对截止时间，防止持久化恢复或时钟异常带来的明显过期数据复活。服务器需正常时间同步。

若必须保证失效任务不丢，需另行设计数据库事务内 outbox 或 CDC；它仍通常是最终一致，不等于强一致。本期不新增表或基础设施来暗中扩大需求。若商品下架必须即时生效，应在展示读取时增加实时数据库状态检查，或只缓存图片/介绍等非状态资料。是否接受展示窗口由用户审阅本方案时决定。

### 4.4 交易不受展示缓存影响

展示价格可能短暂旧，但订单试算、预支付、积分计算、支付和库存校验始终使用现有数据库及支付快照规则。不能在支付时使用展示缓存，也不能因缓存改价更新有效支付快照。房间是否启用、商品是否上架等交易门槛仍在交易入口按现有规则查询验证。

缓存不解决超售；MySQL 事务、行锁、唯一约束和幂等保持原职责。Redis 不参与订单号生成或积分扣减。

## 8. 实施顺序与验收

1. **配置与部署**：修改 pom/application、增加 config 类、Compose/env 示例及部署说明。验收：开关关闭和 Redis 不可用时后端可启动、数据库接口可用；容器健康探针不因可选 Redis 故障反复重启；Redis 不公网暴露。只做配置渲染，不自动部署。
2. **缓存基础设施**：增加缓存接口/实现及 Lua。验收：命中减少 loader 执行；JSON 损坏能回源；旧代次回填被拒绝；所有数据 key 有过期时间；不存在任意类型反序列化或全库删除。
3. **房间与签名接入**：增加房间 DTO，调整两个房间实现及相关测试。验收：同一基础资料供列表/详情复用；available 不进入缓存；封房、支付、取消后日期查询继续使用实时库存；签名不超过其有效期；事务回滚不旋转代次。
4. **商城接入**：增加商品 DTO，修改商品实现及测试。验收：改价/换图/上下架提交后新请求使用新代次；有限分页和详情一起失效；后台查询不受缓存影响；交易试算读取数据库价格。
5. **异常和竞争验证**：完成真实 MySQL+Redis 集成测试。用屏障控制读旧值→提交更新→旧回填的交错，不用 sleep 碰运气；演练 DB 成功/Redis 失败、应用提交后中断、Redis 重连、代次 key 淘汰、缓存全空、并发未命中。
6. **文档与发布准备**：同步 AGENTS、技术指南，记录实测命中率、数据库查询数及接口 P95。先灰度开关启用；关闭开关立即回到直查，不改数据库、不删除图片。

每步依赖前一步完成；1～4 同步写必要单测，5 补充系统性交错和故障用例。所有新增业务类、接口和关键并发逻辑提供准确中文注释。

## 9. 故障、性能与验证细节

- 建议连接超时约 300ms、命令超时约 200ms，实施时根据同机部署实测调整；一次请求多张图片不能每张都等待一次完整故障超时。故障时短时间跳过后续 Redis 请求，批量/流水线读取签名；重试有上限，禁止无限占线程。
- 热点未命中允许数据库回源；首版不额外实现请求合并、分布式锁或缓存预热。只有压测显示热点回源成为问题时，再评估有限合并请求，该合并只为性能，不用于库存正确性。
- 只缓存存在且可展示的数据，不做长期空值缓存。默认分页缓存范围限制内存与随机 key 增长；随机 ID 请求仍需已有参数校验和部署层流量控制，不能伪称不缓存空值已解决穿透。
- Redis 独立缓存实例，设置 maxmemory 和 allkeys-lru 等适用淘汰策略。初期可不启用持久化，避免无必要落盘；重启丢缓存应正常。版本选型在实施时固定镜像版本并核查维护、安全和许可证，不直接使用 latest。
- 只收集命中/未命中、Redis 超时、降级、失效失败/重试、代次拒绝回填等低基数指标；不输出密钥、手机号、签名 URL 或把商品 ID 作为指标标签。利用已有 Actuator/Micrometer，不新增公开指标接口。
- 如果后端在其他节点运行，可选 Redis 故障绕过是各进程局部状态；不能将单机故障标记描述成全局一致性保证。
- 计划验证命令：在 backend 执行 mvn test；集成环境具备 Docker、MySQL 8 与 Redis 时执行所有新增集成测试和受影响 API 回归；使用 docker compose --env-file <本地环境文件> config 验证部署配置但不输出到含敏感值的共享日志。具体命令按仓库运行方式落实。方案阶段尚未执行编译、测试或启动 Redis。

重点验收矩阵：命中/未命中、参数错误、既有权限边界、禁用房间/下架商品、维护事务回滚、图片排序更新、签名到期与轮换、分页总数变化、并发回填、失效失败、Redis 启动不可用/中途断连/恢复、旧价格展示与数据库试算隔离。库存/支付/积分相关既有集成测试继续回归，不能只靠 mock 认定事务及并发正确。

## 11. 可行性、按需存取和可维护性复核

### 11.1 为什么这些数据需要缓存

| 访问路径 | 需要复用的数据 | 选择理由 | 不额外缓存的部分 |
|---|---|---|---|
| 首页/房间列表/房间详情 | 六间房的同一基础目录，含图片引用 | 同一份小数据在多个页面反复读取；一份目录即可供列表和详情使用 | 每个日期组合、可订标记、整套日期响应 |
| 商城列表 | 高频分页及总数 | 当前列表每次需要列表查询和计数；短 TTL 复用可减少重复数据库读取 | 任意页码和 size 的无限组合、后台筛选列表 |
| 商品详情 | 实际被访问的单个商品 | 详情页重复读取、字段变化相对少；按 id 加载，不拉取整个商城 | 未被访问商品、下架/不存在商品的长期占位 |
| 私有房间图片展示 | 需要生成签名的对象 URL | 现有签名方法会创建 COSClient 并计算签名，重复解析同一引用存在可避免的开销 | 已公开 URL 的额外映射、图片文件内容 |

六间房的数据库压力本身有限，不能承诺接入后获得明显性能提升。这里的缓存范围依据重复访问路径选取，最终用 loader 调用次数、Redis 往返开销和接口 P95 判断收益。签名缓存只减少生成链接的工作，不会缩短图片二进制的下载链路。

严格使用懒加载：服务启动不扫描数据库，不提前装入全部商品；第一次实际访问未命中时才加载并写入。只成功查询且符合展示条件的数据才写缓存。有效空商品页可缓存短 TTL 的真实空结果，但数据库异常绝不能转换为空结果写入。命中不续期，不进行后台无限刷新；过期后下一次访问再加载。写操作只失效，不主动预热。

### 11.2 稳定的职责边界

```text
Controller → 现有业务 Service 接口 → ServiceImpl
                                  ├─ 展示读取 → DisplayCacheService → Redis
                                  │               └─ 未命中回调 → 现有 Mapper/XML → MySQL
                                  ├─ 后台/交易 → 原 Mapper/XML → MySQL
                                  └─ 写事务提交成功 → 注册的缓存失效动作
```

ServiceImpl 提供加载回调并负责 Entity → 内部缓存 DTO → VO 的显式转换。通用缓存实现不注入 RoomMapper/MallProductMapper，不理解商品价格、上下架规则或房间库存。Controller 不接触 Redis，不新增缓存 HTTP 接口。

DisplayCacheService 只提供展示快照读取、提交后领域失效、必要的签名复用三类能力；不添加插件注册、自动扫描、动态 SpEL、跨模块业务事件总线或通用分布式锁框架。领域名、缓存结构版本和 key 片段集中声明为具名常量；TTL、页数、超时、重试参数集中配置并校验，禁止散落魔法值。

缓存 DTO 属于内部业务数据输入/输出，不代替对外请求 DTO，也不作为数据库 Entity；字段、金额及时间含义需中文说明。缓存基础设施仅依赖 Spring Data Redis 的 StringRedisTemplate 和应用已有的 Jackson 能力，不添加 Redisson、RedisJSON、MapStruct 或第二级缓存库。

明确类型的序列化由配置/基础设施统一处理；业务模块不散落 ObjectMapper 和字符串 JSON 读写。缓存信封含结构版本、加载时刻、freshUntil 和 payload；列表/详情反序列化必须显式携带类型。对嵌套数组做不可变拷贝，避免后续 VO 装配修改缓存快照。禁止启用任意类型的 Jackson default typing 或使用 JDK 原生对象反序列化。

### 11.3 一致性实现的必要性与约束

本方案没有采用单纯的 @Cacheable + 更新后删除，因为删除后并发旧查询仍可能回填；也没有采用固定延迟双删，因为固定等待时长不能覆盖任意慢查询。保留两个小代次 key 和一段 Lua，其职责仅是把“检查代次”和“写入数据”变成一个原子操作，不在 Lua 编写业务规则。Redis 支持脚本原子执行，但脚本执行期间会占用服务器，因此必须保持常数级操作、无扫描和循环。[Redis 官方脚本说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)

Spring RedisScript 执行机制负责脚本加载及脚本缓存缺失时的回退，不自行维护 SHA 生命周期。数据 key 与代次 key 在脚本中作为 KEYS 参数传入，不能在脚本里拼出未声明的其他 key。

以下细节作为实现验收要求：

- **读请求**：读取代次后再查询数据库；回填比较同一代次。若业务调用已处于可能持有旧数据库快照的事务中，则跳过缓存读写，避免旧事务在新代次下回填旧值。后台和交易分支天然不调用展示缓存。
- **回源只执行必要次数**：Redis GET 失败才回源；MySQL 已成功返回而 Redis SET 失败时，直接返回刚取得的数据，不能再次查询数据库。加载回调抛出的 BusinessException、数据库异常原样交给既有异常处理，不被缓存容错捕获。
- **旧代次回填被拒绝**：最多重新加载一次；持续发生变更时执行一次新直查且不回填，不能无限递归。已启动请求可能返回旧快照的边界仍按第 4 节说明，不承诺强一致。
- **失效时机**：afterCommit 仅执行 Redis 失效和有限调度，不重新进行业务写入或试图回滚已提交事务。缓存失败单独处理，禁止把数据库成功写入误报为失败。Spring 明确 afterCommit 执行时主事务已经提交。[Spring 事务回调说明](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/support/TransactionSynchronization.html)
- **失效重试合并**：按 rooms/mall 两个领域保存至多一个待重试任务，不按请求或商品 id 无限排队；同一领域的新更新可合并。达到重试上限后记录失败并依赖缓存有效期，不永久占用请求线程。
- **绝对截止时间**：加载开始时确定截止时间，回填时只给剩余 TTL。回填脚本使用明确的截止时间与 Redis 服务端时间校验，不能把慢查询前计算的完整 TTL 原样用于晚到的 SET；value 的截止时间作为读时第二道检查。时钟同步是建议窗口成立的运行前提，不能承诺网络分区下的绝对实时。
- **更新覆盖**：六个现有维护入口必须全部注册失效；同事务重复注册同一领域时合并。新增写入口必须遵循同一规则。图片上传仅产生对象 URL，只有保存到房间/商品资料后才改变展示缓存；无需仅因上传了一个尚未引用的文件就失效整个目录。
- **外部改库**：人工 SQL、导入脚本或未来其他服务直接写 room/mall_product 不会自动触发 Java 回调；运维需关闭缓存或执行指定领域失效后再恢复。数据库外部写入的补偿必须写入部署文档，不能宣称代次覆盖了全部外部变更。

已复核当前 Java 和 MyBatis 写路径：房间资料写入集中于 RoomServiceImpl 的三个维护方法，商城商品写入集中于 MallProductServiceImpl 的三个维护方法。room_block、订单等其他表的写入不失效基础目录，因为实时可订结果未缓存。商城订单查询虽关联 mall_product.images，仍保持原查询，不顺带缓存会员订单。

商城分页的列表与总数来自现有两条 SQL，“装进同一个缓存 value”本身不保证它们来自同一数据库快照。首版复用现有分页契约，不新增更强的快照承诺；加载期间成功切换代次则拒绝回填。若后续要求并发商品维护下 list/total 严格同快照，需要在业务加载层单独设计短只读事务，不能把 SQL 或数据库事务职责移入 Redis 基础设施。

### 11.4 可运行和可测试的完成标准

| 场景 | 可观察的验收结果 |
|---|---|
| 冷启动且无页面访问 | Redis 不出现全部商品数据；不触发批量数据库预热 |
| 首次访问一件商品 | 只新增该商品实际使用的数据 key 和领域元数据 |
| 重复访问房间目录/商品 | 有效缓存命中，相关基础资料 loader 调用次数减少；日期库存检查继续执行 |
| 后台更新、换图、上下架 | 正常提交并完成代次切换后，之后发起的查询不再命中旧代次；列表和详情同时失效 |
| 写事务回滚 | 数据库不变、缓存代次不变，不产生假成功结果 |
| 更新与旧查询交错 | 使用线程屏障可稳定复现，Lua 拒绝旧代次回填 |
| 数据库成功、Redis 写入失败 | 返回已有数据库结果，不重复 loader；维护接口不误报数据库回滚 |
| Redis 不可达/重启 | 缓存绕过、接口数据库回源；不会让健康探针导致容器反复重启 |
| 私有签名接近到期 | 返回前刷新签名，不把过期链接留在长寿命房间快照中 |
| 配置开关关闭 | 缓存完全绕过、原数据库业务链路仍可运行 |

单元测试默认关闭真实缓存，通过 DisplayCacheService 接口替身验证调用与失效注册；增加构造器依赖后同步更新现有测试实例化，不保留测试专用隐藏构造器。Redis 和 MySQL 集成测试显式开启缓存并使用独立随机命名空间，测试结束仅清理本命名空间，禁止清空共享 Redis。使用真实 Spring 代理验证事务提交/回滚回调，直接 new ServiceImpl 的 mock 测试不算事务验证。

开发时遵守项目规范：保留包名与 Controller → Service 接口 → ServiceImpl → Mapper/XML 分层；不把 SQL 放进注解或缓存类；修改范围内补充类/接口方法中文 JavaDoc；采用现有构造器注入；金额 BigDecimal、id Long；配置默认值有名有据；不重构无关模块。无 API/schema 变更则不创建迁移，不修改已应用迁移。

本次可行性结论：当前 Spring Boot/MyBatis/COS 架构可直接接入该展示缓存，不需要数据库迁移或前端改造。主要成本是统一缓存适配器、三个业务实现的接入和真实故障/竞争测试。风险集中于展示陈旧窗口、失效失败和私有签名到期，前述机制分别提供显式边界与补偿。方案审阅完成后再进入应用代码实施，不能把方案文档视作已实现或已验证。

## 12. 环境变量最小集合（用户明确要求）

Redis 相关 .env 配置仅保留以下四项，不把缓存策略参数逐项暴露为环境变量：

```dotenv
# 是否启用展示缓存
DISPLAY_CACHE_ENABLED=false

# Compose 内使用 redis；后端直接在宿主机运行时按部署实际调整
REDIS_HOST=redis
REDIS_PORT=6379
REDIS_PASSWORD=<部署时填写>
```

密码不进入仓库，.env.example 仅放占位说明；不得为增加 Redis 覆盖已有环境文件中的其他配置。

连接/命令超时、各类 TTL、分页缓存范围、内存限制、淘汰策略、数据库编号、缓存结构前缀、签名刷新余量与有限重试参数，统一在 application.yml 或 docker-compose.yml 的对应位置集中定义；不增加逐项环境变量映射。算法常量与固定 key 片段使用具名常量，避免散落魔法值。

当前自建内网 Redis 使用默认数据库和密码认证，不预设用户名、TLS 等额外环境变量；未来部署确有需求再按需添加。开发、测试、生产使用独立 Redis 部署/测试随机命名空间；结构版本保留在统一 key 前缀中，无需为此前缀单独增加 .env 参数。

本节覆盖前文有关“超时、TTL 等可配置”的环境变量解释：可集中配置，不代表都应进入 .env。实际部署文件修改仍属于后续实施，本次只更新方案。

## 13. 实施记录（2026-11-28）

用户随后明确不需要 Redis 开关和密码，最终部署环境变量仅为 REDIS_HOST 和 REDIS_PORT；第 12 节示例中的开关和密码不适用。当前实现将 TTL 与分页范围集中在 application.yml 和强类型配置中，不暴露额外环境变量。缓存读取与失效由 DisplayCacheService / RedisDisplayCacheService 实现；代次比较和绝对过期写入使用简短 Lua 脚本。失败失效每领域后台最多重试三次，下一次访问也会重试，失败时回源；该重试不持久化；其他进程和提交后崩溃仍依靠 TTL。当前已添加命中、未命中、读写失败、失效失败和拒绝回填计数；展示资料使用随机 TTL；持久化失效队列和分布式缓存热点击穿保护不在首期范围，不应据此声称这些能力已完成。缓存部署依赖可信内网隔离，不配置密码。此记录是实际实现说明，覆盖上文未落地的具体实现设想。
