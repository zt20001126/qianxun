# 指定日期节假日价实施方案

日期：2026-11-28  
状态：2026-11-28 已确认，实施参照

## 推荐方案

采用「客房表保存两档金额，独立日期表保存全店启用日，后端统一计价」的结构。金额配置和日期配置各有唯一来源，修改一次日期即可覆盖全店，调整某个房间的金额也只需修改该房间。数据库现有迁移中没有通用的全店配置表。独立日期表可直接做月份和住宿区间查询，并用唯一约束保证日期只保存一次。管理员修改某一天时只更新对应记录，其他日期可独立维护。

日期表采用项目约定的 `BIGINT UNSIGNED` 自增主键，`holiday_date` 作为业务唯一键和日期查询索引。表中一行代表一个已启用节假日价的日期，勾选插入，取消删除。

将来如需按房间配置启用日或使用第三档价格，先扩展日期匹配和定价服务，再由现有报价入口读取新结果。支付和历史订单继续消费交易快照中的金额。这一版的表结构和接口只承载全店共用日历和两档价格。

## 经营规则

- **设金额。** 管理员进入「客房管理 → 编辑」，填写该房间的平时价和节假日价并保存。
- **设启用日期。** 管理员进入「客房管理 → 节假日价格日历」，切换到目标月份，勾选日期后保存。勾选就是为该日期开启节假日价，取消勾选并保存就是将该日期恢复为平时价。日历按全店共用一份设计，六间房分别使用自己保存的金额。普通周末同样依据勾选结果计价。
- **提前预订。** 日期保存后就参与新报价。系统以北京时间的住宿夜晚匹配配置。后台可提前配置未来月份，小程序仍按北京时间 60 个自然日的预订窗口开放预订。
- **逐晚合计。** 入住日计费，退房日不计费。比如管理员只勾选 2027 年 1 月 1 日，101 房平时 298 元、节假日 398 元。客人 2026 年 12 月 10 日预订 12 月 31 日入住、1 月 2 日退房，房费是 298 + 398 = 696 元。
- 房价或日历变动对新报价和新预支付生效。已创建且仍有效的预支付使用原金额快照，已生成的订单使用原交易金额。跨月经营报表仍按已确认口径平均分摊实际订单金额，分币尾差归最后一晚。

## 数据库改动

| 表或字段 | 方案 | 迁移与兼容 |
| --- | --- | --- |
| `room.price` | 作为平时价，继续使用 `DECIMAL(12,2)` | 字段名、类型及已有金额沿用。 |
| `room.holiday_price` | 新增可空 `DECIMAL(12,2)`，约束为非负 | 存量房间默认空，未配置时使用该房间平时价。可兼容仍只写 `price` 的旧库导入脚本和旧客户端。配置为 0 时按 0 计价。 |
| `holiday_price_date.id` | 新增表的 `BIGINT UNSIGNED AUTO_INCREMENT` 主键，MySQL 8 InnoDB | 沿用本项目主键约定，供持久化使用。 |
| `holiday_price_date.holiday_date` | `DATE NOT NULL`，新增唯一索引 `uk_holiday_price_date` | 每个选中日期保存一行。唯一索引用于按月及住宿区间查询，防重复勾选。初始为空，取消勾选删除记录。 |
| `booking_lock.room_amount / discount_amount / amount` | 复用预支付金额快照 | 新交易写入逐晚合计及现有积分计算结果。已有记录继续读原值。 |
| `orders`、`order_amount`、`payments`、`room_block` | 继续使用现有结构 | 订单、实付、退款和报表从交易快照或既有金额取值。日期配置只影响定价。 |

拟新增 `backend/src/main/resources/db/migration/V23__add_holiday_room_pricing.sql`，序号以实施时最后一条迁移为准。先随兼容后端运行 Flyway，再发布管理后台和小程序。应用回退时可保留新增数据结构及配置，回退版本的新报价会恢复单一平时价，应在回退前评估这一行为。已应用的迁移文件保留原样。

## 接口改动

| `PUT /api/admin/rooms/{id}/enabled` | 入参及启停行为沿用，房间响应随共用 VO 增加 `holiday_price`。 |
| `GET /api/admin/holiday-price-dates?month=YYYY-MM` | 新增。管理员按月查询，返回该月已配置日期列表 `dates`，日期格式 `YYYY-MM-DD`。 |
| `PUT /api/admin/holiday-price-dates` | 新增。管理员提交当月 `month` 以及点选变更 `add_dates`、`remove_dates`，返回更新后的 `dates`。服务端校验月份、日期及两组互斥，单事务应用变更。重复加选或取消结果一致，两个管理员改不同日期时各自的修改都可保留。两个接口沿用后台鉴权及统一响应，非法输入返回 400。 |
| `GET /api/app/rooms` | 有入住和退房日期时增加 `room_amount`，表示该区间的房费总额。原 `price` 继续表示平时价，兼容旧调用。 |

| `POST /api/app/rooms/availability-check` | 结构沿用，`room_amount` 更新为逐晚合计。 |
| `POST /api/app/points/preview` | 结构沿用，试算使用房态复核提供的逐晚房费总额，原积分抵扣规则继续适用。 |
| `POST /api/app/payments/prepay` | 结构沿用。现有预支付事务内重新查库计算，创建成功时保存快照。模拟支付及现有微信支付后续入口继续使用交易金额。 |

主要调用关系

```text
客房管理页 → 客房接口 / 节假日日期接口 → room / holiday_price_date
小程序客房列表、房态复核、预支付 → RoomPriceService → 房间两档价 + 日期清单
积分预览 → 房态复核 → 房费总额
支付及建单 → 已锁定交易金额 → 订单金额快照
```

## 价格计算与校验

`RoomPriceService` 按 `check_in <= holiday_date < check_out` 读取日期。用住宿晚数减去命中日期数得到平时晚数，再以两档的金额乘各自晚数并求和。节假日价为空时以平时价代入。后端使用 `LocalDate` 和 `BigDecimal`，对外继续返回两位小数的金额字符串。超出金额快照字段 `DECIMAL(12,2)` 上限的报价返回 422。

后台保存日期与房间价格分别提交。房间定价在客房更新事务提交后可供新报价使用，日期变更在日期事务提交后可供新报价使用。区间报价和预支付均直接从数据库取得计价数据，已有 Redis 仅服务客房资料展示。预览之后若发生改价，预支付按当时的配置重新算价，后续付款确认页展示预支付锁定金额。

## 实施与验收顺序

1. 落实契约和 Flyway 迁移。用存量房间和旧房间写入测试验证迁移成功、初始日期清单为空，存量平时价和原订单金额一致。
2. 接通客房维护与日期管理。管理员可按月读写日期，未授权访问被拒绝。覆盖非法日期、跨月数据误提交、同日冲突、重复请求和旧客房编辑请求保留节假日价。六间房能保存各自不同的金额。
3. 接通逐晚报价和交易快照。覆盖全平时、全节假日、混合连住、跨月、退房日命中节假日、未配置节假日价和普通周末按平时价。用在预订窗口开放前提前保存的未来日期，验证窗口开放后可按节假日价预订。验证列表、房态复核、积分试算、预支付总额一致，变更配置后有效待付金额及订单历史金额一致。付款方式、库存窗口和报表分摊走原流程。
4. 完成两端展示和交互。后台能够选中和取消日期并在刷新后还原；小程序显示所选区间总额，预订和订单页面金额与后端一致。复用项目检查命令 `mvn -s backend/maven-settings/aliyun.xml -f backend/pom.xml test`、`npm --prefix frontend/admin run build`、`npm --prefix frontend/miniprogram run typecheck`。MySQL 8 回归使用 Docker/Testcontainers，小程序价格展示在微信开发者工具验证。

该方案由 Flyway V23 和客房定价模块实现，相关回归使用本节列出的验证入口。
